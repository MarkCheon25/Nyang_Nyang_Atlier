| 층 | 내용 |
|---|---|

| **PC 쪽** | `hcr_control` 패키지 = **`hardware_interface::SystemInterface` 구현** |

## 4. 실기 연결 경로 — 방향은 (A), 다만 **지금은 버전에 막혀 있다**

| 경로 | 상태 |
|---|---|
| **(A) ros2_control SystemInterface** | 구조는 ✅ 실증됨 (`hcr_control/RobotSystem`) — **그러나 §4.1 로 현재 차단** |
| (B) 궤적 → Rodi 명령 브릿지 | (A) 의 관문이 안 열릴 때의 대안 |

(A) 가 열리면 `joint_trajectory_controller` · MoveIt2 · 하드웨어 추상화 경계(N6·F7.3)가 **전부 그대로 성립한다.**

### 4.1 ⛔ 차단 지점 — Rodi 버전 미달 (2026-07-28 실측)

| 구분 | Rodi 버전 | 비고 |
|---|---|---|
| **우리 로봇 (실측)** | **`1.003.005`** | 컨트롤러 SW `1.003.001` |
| 매뉴얼(2018) 스크린샷 예시 | `2.000.001.002` | 컨트롤러 `1.006.000` |
| **플러그인 최소 요구** | **`2.001.003.012`** | `package.json` 의 `minimumRequiredVersion` |
| 저자(그단스크) 환경 | `2.005.008.009_G2` | `rodiVersion` |

**메이저 버전이 1 vs 2 — 지금 이 로봇에는 `ROS2.asar` 를 설치할 수 없다.**

RoboDK 가 요구하는 버전(`2.001.003.012`)과 이 플러그인의 최소 요구가 **정확히 같다.**
그 버전이 **Rodi-X 플러그인 확장 기능이 도입된 시점**으로 보이며, 1.x 대에는 플러그인 메커니즘 자체가 없다.
공식 매뉴얼 목차에 "Rodi-X Plug-in" 메뉴가 없던 것(§3.4)과도 일치한다.

### 4.2 뚫는 방법 — Rodi 업그레이드 (매뉴얼 §16.6 에 정식 절차 존재)

```
메인 메뉴 ⇒ SW Configuration ⇒ SW Update
  · Rodi Software       — 업데이트 파일 확장자 .tgos
  · Controller Software — 확장자 .run
```

- **USB 등 외부 저장장치로만** 가능. TP 보다 **컨트롤러에 직접 연결** 권장 (데이터가 커서 TP 경유는 실패할 수 있음)
- ⚠️ **운영 SW 와 컨트롤러 SW 를 서로 호환되는 버전으로 함께** 올려야 한다 — 매뉴얼이 *"비호환 버전을 설치하면 로봇이 정상 동작하지 않을 수 있다"* 고 명시
- ⚠️ **일반 사용자 권한으로는 불가**. 매뉴얼이 *"한화정밀기계 또는 지역 서비스센터에 문의"* 하라고 안내

> **정황 (가설)** — 2018년 매뉴얼 스크린샷에 이미 Rodi `2.000.001.002` 가 찍혀 있다.
> 즉 2.x 계열은 **이 로봇 세대에 이미 배포되던 버전**이며, 우리가 1.003.005 인 것은 하드웨어 한계가 아니라
> **출고 후 한 번도 올리지 않았기 때문일 가능성이 크다.** 단정은 못 한다 — 스크린샷은 예시이고,
> 2.000.x 조차 플러그인 요구(2.001.003.012)에는 미달이다. 다만 **"1.x → 2.x 가 원래 불가능한 벽은 아니다"** 는 근거는 된다.

### 4.3 관문이 열린 뒤에도 남는 위험 3가지

1. **명령 분해능 `%7.2f` = 0.01°** — reach 915 mm 에서 약 **0.16 mm** (0.01° = 1.745e-4 rad × 915 mm).
   로봇 반복정밀도 ±0.1 mm 와 같은 자릿수라 **선 품질의 병목이 될 수 있다.**
2. **`read()` 가 `send`→`recv` 블로킹** — controller_manager 100 Hz 를 유지하려면 왕복이 10 ms 안에 끝나야 한다.
3. **`MOV` 를 로봇이 어떻게 해석하는가** — 점대점(movej)인지 서보 추종인지에 따라 연속 궤적 품질이 갈린다.

### 4.4 관문이 안 열리면

- **(B) 브릿지** — Rodi 1.x 가 제공하는 외부 통신은 Modbus TCP(I/O·레지스터)뿐이라, 좌표를 레지스터로 넘기고
  로봇 측 프로그램이 읽어 이동하는 핸드셰이크 방식이 된다. **스트로크 수천 개인 선화에는 속도·품질 모두 불리하다.**
- **Phase 1 을 sim 으로 완주** — 애초의 프로젝트 목표(README: *"MoveIt2 mock + RViz2 에서 선화 완주"*)이며,
  실기는 Phase 2 로 미룬다. **R1 이 소프트웨어 개발 전체를 막지는 않는다**(BRD §6 R1 원문과 동일한 판단).

## 5. 실기 연결 전 반드시 교체할 값 — 공식 스펙 대조

### 5.1 관절 속도 한계 — 현재 실기의 약 32배

`joint_limits.yaml` 의 `max_velocity: 100.0` (rad/s) = **5729 °/s**.
**HCR-5 공식 최대 관절속도는 180 °/s (= 3.1416 rad/s)** — Appendix G 가 *"maximum speed of 180°/sec which can be generated at the robot joint"* 로 명시.

`velocity_scaling_factor` 0.1 로 큰 이동(joint_1 약 4 rad)을 계획시킨 실측:

```
joint       peak rad/s  peak deg/s   HCR-5 공식     배율
joint_1          6.002       343.9         180      1.91x
```

**스케일링 0.1 에서도 약 1.9배, 1.0 이면 약 19배**다. URDF `<limit ... velocity="100"/>` 과 `joint_limits.yaml` **양쪽 모두** 고쳐야 한다.

`max_acceleration: 100.0` 도 임시값이다. **공식 매뉴얼에 관절 최대 가속도 항목이 없다** — Appendix G 의 정지거리·정지시간(J1 34.67°/0.61 s, J2 31.60°/0.55 s, J3 29.08°/0.51 s, 브레이크 체결 0.03 s)에서 역산하거나 벤더에 문의해야 한다.

### 5.2 관절 가동범위 — CAD 변환값이라 실기와 불일치

| 관절 | URDF | **HCR-5 공식 (Appendix F)** | 문제 |
|---|---|---|---|
| joint_1 | **0° ~ +360°** | ±360° | **음수 방향 불가** |
| joint_2 | ±90° | ±360° | 크게 좁음 |
| joint_3 | ±130° | **±165°** | 좁음 (J3 만 별도 제한이 실제로 존재) |
| joint_4 | ±170° | ±360° | 좁음 |
| joint_5 | ±120° | ±360° | 좁음 |
| joint_6 | **0° ~ +360°** | ±360° | **음수 방향 불가** |

공식값은 `±360° (J3: ±165°)` 한 줄이다. joint_1·6 의 음수 불가가 특히 문제로,
**IK 해가 있는데도 F4.2 가 계획 실패로 떨어질 수 있다.**

> URDF 한계를 실기보다 **좁게** 두는 것은 안전하지만, 넓게 두면 로봇이 자체 정지를 건다 (매뉴얼 8.5 *Exceeding Safety Limit of Joints*).

### 5.3 effort

URDF `effort="100"` 도 CAD 기본값이다. 공식 매뉴얼에 관절 토크 항목이 없어 벤더 문의 대상이다.

### 5.4 확정된 실물 제원 (Appendix F)

| 항목 | 값 |
|---|---|

## 6. 다음 확인 순서

> **"Rodi 버전을 확인한다"는 1순위 과제는 2026-07-28 완료됐다** — 결과가 §4.1(미달)이다. 그래서 순서가 아래로 바뀌었다.

### 6.1 지금 1순위 — 벤더 문의 (질문이 하나로 좁혀졌다)

이전의 막연한 질문("실시간 제어 인터페이스가 있습니까")은 폐기한다. 지금은 이것 하나다:

> **"HCR-5(구형)용 Rodi `2.001.003.012` 이상 업데이트 파일(`.tgos`)과, 그에 호환되는 컨트롤러 소프트웨어(`.run`)를 받을 수 있습니까?"**

담당자가 예/아니오로 답할 수 있고, **그 답이 (A)/(B) 를 가른다.** 단종 모델이라도 서비스센터에 과거 릴리스가 남아 있을 수 있다.

함께 물을 것:

1. 업그레이드 시 **기존 티칭 프로그램·설정의 호환성** (이 로봇으로 하던 다른 작업이 있다면 필수)
2. 단종 모델 **업그레이드 지원 가능 여부**와 절차 (서비스센터 방문이 필요한지)
3. 관절별 **최대 가속도 · 최대 토크** — 공식 매뉴얼에 항목이 없다 (§5.1·§5.3)
4. 외부 제어 중 **안전 정지(F6 긴급정지)** 동작 방식

문의처: `robot_inquiry@hanwha.com` 또는 지역 서비스센터

### 6.2 업그레이드가 성사되면

1. **`ROS2.asar` 설치** (`Management ⇒ Rodi-X Plug-in`) → 데몬 기동 확인
2. **포트 6667 개방 확인** (`rahulantonyp/Hanwha` 의 `OpenPortsCheckHCR12.ipynb` 참고)
3. `hcr_control` 을 워크스페이스에 붙이고, xacro 를 `ros2_control:=false` 경로로 돌려 **IP·포트 `<param>` 을 담은 자체 블록** 작성
   (mock 은 파라미터가 없어 현재 매크로에는 넣을 자리가 없다 — simulation 이 쓰는 그 경로를 실기도 탄다)
4. `MOV` 처리 방식 확인 (`hcr_plugin/ROS2` 소스) — 점대점 / 서보 추종
5. 0.01° 분해능이 선화 정밀도 요구를 만족하는지 계산 (§4.3-1)

### 6.3 업그레이드와 무관하게 지금 할 수 있는 것

- **`joint_limits.yaml`·URDF 를 공식값으로 교체** (§5) — 값이 이미 확보되어 있어 즉시 착수 가능하고, 실기 연결 전 **반드시** 끝나야 한다
- **Phase 1 을 sim 으로 완주** — R1 은 실물 실행만 막고 소프트웨어 개발 전체를 막지 않는다

```bash
cd Nyang_Nyang_Atlier/src/moveit2
./run_container.sh build          # moveit2_dev:jazzy 미빌드 시 (20~40분)
./run_container.sh shell

ros2 launch hcr_moveit_config demo.launch.py    # ⚠️ 두 번 실행 금지 (포팅 문서 문제 4)
```

**상태 확인** (다른 터미널):

```bash
ros2 control list_controllers            # 둘 다 active 여야 함
ros2 control list_hardware_components    # plugin name 으로 mock/실기 판별 ★
ros2 topic echo /joint_states --once
```

`list_hardware_components` 의 `plugin name` 이 **지금 무엇에 연결되어 있는지 판별하는 가장 빠른 방법**이다.

**RViz 없이 팔 움직이기**:

```bash
ros2 topic pub -1 /hcr_arm_controller/joint_trajectory trajectory_msgs/msg/JointTrajectory "{
  joint_names: [joint_1, joint_2, joint_3, joint_4, joint_5, joint_6],
  points: [{positions: [0.5, 0.0, 1.5669, -1.59, -1.4695, 0.0], time_from_start: {sec: 2}}]}"
```
