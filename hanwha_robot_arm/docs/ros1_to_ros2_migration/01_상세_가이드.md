## 1. 왜 이 작업이 필요했나 (Why)

### 1.1 처음 증상

`ros2_ws`를 빌드하면 `hcr_robot_description` 패키지에서 다음 에러가 발생:

```
CMake Error at CMakeLists.txt:10 (find_package):
  By not providing "Findcatkin.cmake" in CMAKE_MODULE_PATH this project has
  asked CMake to find a package configuration file provided by "catkin"...
```

### 1.2 근본 원인

`hcr_robot_description`의 `CMakeLists.txt`가 `find_package(catkin REQUIRED COMPONENTS rospy)`를 호출하고 있었음. 이는 **ROS1(catkin) 전용 문법**인데, 정작 이 패키지가 들어있는 워크스페이스 이름은 `ros2_ws`이고 설치된 ROS는 **ROS2 Jazzy뿐**(`ROS_DISTRO=jazzy`, `/opt/ros/noetic` 등 ROS1은 시스템에 아예 없음)이었음.

조사 결과, 문제는 이 패키지 하나가 아니라 **저장소 전체**였다:

- `hcr_robot_description` — SolidWorks→URDF 변환 툴(`sw_urdf_exporter`/`fusion2urdf`)이 생성한 순수 ROS1 catkin 패키지. `package.xml`에 `<buildtool_depend>catkin</buildtool_depend>` 명시.
- `hcr_moveit` — **MoveIt1 Setup Assistant**가 생성한 전형적인 ROS1 구조. `fake_controllers.yaml`, `ros_controllers.yaml`, `setup_assistant.launch` 등 ROS1/MoveIt1 전용 파일들로만 구성. `launch/` 안의 모든 파일이 `.launch`(ROS1 roslaunch XML)이고 ROS2용 `.launch.py`는 하나도 없음.
- 저장소 `README.md`도 2023년 ROS1 전제로 작성됨.

즉, catkin 에러는 빙산의 일각이었고 실제로는 **"ROS1 패키지를 ROS2 워크스페이스에 그대로 넣어둔 상태"** 였다.

### 1.3 왜 "빌드에서 제외"만으로는 안 되는가

처음에 고려한 옵션: `COLCON_IGNORE`로 `hcr_moveit`/`hcr_robot_description`을 빌드에서 빼고 launch 파일만 그대로 쓰면 안 되는가?

**안 된다.** 이유 두 가지:

1. 빌드에서 제외된 패키지는 `install/`에 설치되지 않으므로 ROS2 패키지 인덱스에 잡히지 않는다. `ros2 launch hcr_robot_description display.launch` 같은 명령이 "package not found"로 실패한다.
2. `.launch` 파일은 ROS1 roslaunch의 XML 문법(`<node pkg=... type=... name=...>` 등)으로 작성되어 있는데, `ros2 launch`는 이 문법 자체를 이해하지 못한다. 확장자를 바꿔도 내용 문법이 다르기 때문에 실행이 안 된다.

따라서 실제로 launch까지 쓰려면 **CMake/패키지 매니페스트뿐 아니라 launch 시스템까지** ROS2 방식으로 다시 작성해야 한다.

### 1.4 대안: ROS1 Docker vs ROS2 정식 포팅

- **ROS1 Docker(예: `osrf/ros:noetic-desktop-full`)**: 기존 저장소가 100% ROS1이므로 코드 변경 없이 즉시 돌아감. 빠르지만 결국 ROS2 환경과 별개의 컨테이너.
- **ROS2 Jazzy/MoveIt2 정식 포팅**: 시간이 더 걸리지만 지금 쓰는 `ros2_ws`와 완전히 통합됨.

사용자가 **ROS2 정식 포팅**을 선택하여 이 문서에 정리된 작업을 진행함.

## 2. 무엇을 했나 (What) — 변경 사항 전체 목록

### 2.1 `hcr_robot_description` (catkin → ament_cmake)

| 파일 | 조치 |
|---|---|
| `CMakeLists.txt` | catkin 빌드 로직 전체 삭제 → `ament_cmake` 기반으로 재작성. `urdf/`, `meshes/`, `launch/`를 `share/${PROJECT_NAME}`에 설치 |
| `package.xml` | `format="2"` + `catkin`/`rospy` 의존성 → `format="3"` + `ament_cmake` buildtool, `xacro`/`robot_state_publisher`/`joint_state_publisher_gui`/`rviz2` exec_depend로 교체 |
| `urdf/hcr_robot.ros2_control.xacro` (신규) | `ros2_control` 태그 블록 추가. 하드웨어 플러그인은 `mock_components/GenericSystem`(가짜/시뮬레이션 하드웨어). 6개 조인트(`joint_1`~`joint_6`) 모두 `position` command/state, `velocity` state 인터페이스 정의 |
| `urdf/hcr_robot.xacro` | 위 ros2_control 매크로를 `xacro:include` + 인스턴스화하도록 3줄 추가 |
| `launch/display.launch.py` (신규) | 기존 `display.launch`(ROS1)를 대체. `robot_state_publisher` + `joint_state_publisher_gui` + `rviz2`로 단독 URDF 시각화 |

> 기존 `hcr_robot.trans`(ROS1 `transmission_interface`)와 `hcr_robot.gazebo`(Gazebo Classic 플러그인)는 그대로 남겨둠 — URDF 파서가 무시하는 태그라 파싱에 지장이 없고, 이번 작업 범위(RViz+mock hardware로 MoveIt 테스트)에서는 쓰이지 않기 때문. Gazebo 연동은 이번 포팅 범위 밖.

### 2.2 신규 패키지 `hcr_moveit_config` (MoveIt2 설정 패키지)

기존 `hcr_moveit`(MoveIt1 Setup Assistant 산출물)을 그대로 포팅하지 않고, **ROS2 Jazzy의 표준 MoveIt2 설정 패키지 레이아웃**(`moveit_configs_utils.MoveItConfigsBuilder`가 기대하는 구조, `moveit_resources_panda_moveit_config`를 레퍼런스로 참고)에 맞춰 새로 구성함.

| 파일 | 출처/내용 |
|---|---|
| `CMakeLists.txt`, `package.xml` | 신규 작성 (ament_cmake) |
| `config/hcr_robot.urdf.xacro` | 신규 — `hcr_robot_description`의 `hcr_robot.xacro`를 `$(find ...)`로 include하는 얇은 래퍼 |
| `config/hcr_robot.srdf` | `hcr_moveit/config/hcr_robot.srdf`에서 **그대로 재사용** (SRDF 포맷은 MoveIt1/2 동일) + `<virtual_joint>` 추가 (아래 참고) |
| `config/kinematics.yaml` | 그대로 재사용 (KDL 플러그인 설정은 MoveIt1/2 동일) |
| `config/joint_limits.yaml` | 재사용하되 타입 버그 수정 (3.1절 참고) |
| `config/ompl_planning.yaml` | 재사용하되 필수 키 3종 추가 (3.2절 참고) |
| `config/moveit_controllers.yaml` | 신규 — `moveit_simple_controller_manager` 설정. `hcr_arm_controller` (FollowJointTrajectory) |
| `config/ros2_controllers.yaml` | 신규 — `ros2_control`의 `controller_manager` 설정. `joint_state_broadcaster` + `hcr_arm_controller`(`joint_trajectory_controller`) |
| `config/moveit_cpp.yaml` | 신규 — Python API(`moveit_py`)로 스크립팅할 때 필요한 설정 (자동검증 스크립트 작성 중 필요성 확인) |
| `launch/demo.launch.py` | 신규 — `move_group` + `rviz2` + `static_transform_publisher`(world→base_link) + `robot_state_publisher` + `ros2_control_node` + 컨트롤러 스포너 2개를 한 번에 기동 |
| `launch/moveit.rviz` | 신규 — `MotionPlanning` 디스플레이 포함 RViz 설정. Fixed Frame `world`, Planning Group `hcr_arm` |

**`hcr_robot.srdf`에 virtual_joint를 추가한 이유**: 원본 ROS1 SRDF에는 `virtual_joint`가 없어서 로봇의 루트 링크(`base_link`)가 어떤 좌표계에도 고정되어 있지 않았음. `<virtual_joint name="virtual_joint" type="fixed" parent_frame="world" child_link="base_link"/>`를 추가하고, launch에서 `world`→`base_link` 정적 TF를 같이 publish해서 RViz의 Fixed Frame을 `world`로 잡을 수 있게 함 (moveit_resources_panda_moveit_config의 관례를 따름).

**초기 관절 각도 변경**: `hcr_robot.ros2_control.xacro`의 각 조인트 `initial_value`를 전부 0이 아니라 SRDF의 `hcr_home` group_state 값(`joint_3=1.5669, joint_4=-1.59, joint_5=-1.4695`, 나머지 0)으로 맞춤. 전부 0인 자세는 `joint_1`/`joint_6`의 관절 하한(0 rad)에 걸쳐 있는 경계값이라 플래닝 테스트에 불리하기 때문.

### 2.3 레거시 패키지 처리

`hcr_moveit`(ROS1) 디렉토리에 `COLCON_IGNORE` 파일을 추가하여 colcon 빌드 대상에서 제외. 안의 설정값은 이미 `hcr_moveit_config`로 옮겨졌으므로 내용 손실은 없음. 이 조치가 **최초에 보고된 catkin 에러의 직접적인 해결책**이기도 함.

## 3. 중간에 안 됐던 것들 — 무엇이, 왜 실패했고, 무엇을 해서, 왜 해결됐는가

포팅 자체(파일 작성)는 문법 오류 없이 끝났지만, **실제로 `move_group`을 띄우고 계획을 실행해보는 단계**에서 총 4가지 문제가 순차적으로 발견됨. 모두 "ROS1과 ROS2/MoveIt2의 암묵적 규칙 차이"에서 비롯된 문제로, 문서/튜토리얼만 봐서는 알기 어렵고 실제로 돌려봐야 드러나는 종류의 버그였음.

### 3.1 버그 1 — `joint_limits.yaml` 정수/실수 타입 불일치

- **증상**: `ros2 launch hcr_moveit_config demo.launch.py` 실행 시 `move_group`이 시작하자마자 죽음.
  ```
  terminate called after throwing an instance of 'rclcpp::exceptions::InvalidParameterTypeException'
    what():  parameter 'robot_description_planning.joint_limits.joint_1.max_velocity' has invalid type: expected [double] got [integer]
  ```
- **왜 발생했나**: 원본 YAML에 `max_velocity: 100`처럼 정수 리터럴로 적혀 있었음. ROS1의 파라미터 서버는 타입이 느슨해서 이 값을 문제없이 double로 취급했지만, **ROS2의 파라미터 시스템은 엄격하게 타입을 검사**한다. `joint_limits` 항목 전체가 double 타입으로 선언되는데 정수 리터럴이 섞여 있으면 즉시 예외를 던지고 프로세스가 죽는다.
- **무엇을 했나**: `joint_limits.yaml`의 모든 `max_velocity: 100` → `max_velocity: 100.0`, `max_acceleration: 0` → `max_acceleration: 0.0`으로 수정 (정수를 명시적 실수 리터럴로 변경).
- **왜 이렇게 해야 하나**: YAML 파서 입장에서 `100`과 `100.0`은 각각 int/float로 타입이 확정되고, ROS2 노드가 해당 파라미터를 선언할 때 기대하는 타입(double)과 일치해야 로드가 성공하기 때문. 값 자체는 동일하지만 "타입 표기"를 명시적으로 맞춰야 한다.

### 3.2 버그 2 — `ompl_planning.yaml`에 `planning_plugin`이 없음

- **증상**: 버그 1을 고친 뒤 재실행하면 `move_group`이 다시 죽음.
  ```
  terminate called after throwing an instance of 'std::runtime_error'
    what():  Planning plugin name is empty or not defined in namespace 'ompl'. Please choose one of the available plugins: ...
  ```
- **왜 발생했나**: ROS1/MoveIt1에서는 `planning_plugin` 파라미터를 `ompl_planning_pipeline.launch.xml` 같은 **별도 launch 파일**에서 `<param name="planning_plugin" value="ompl_interface/OMPLPlanner"/>`로 지정했다. 그런데 원본 저장소에서 가져온 `ompl_planning.yaml`에는 planner_config 목록만 있고 이 파라미터가 없었음. MoveIt2(`MoveItConfigsBuilder`)의 관례는 **파이프라인 yaml 파일 자체에 `planning_plugins`/`request_adapters`/`response_adapters` 키를 직접 넣는 것**이라, launch 파일에서 이 값을 채워주지 않으면 아예 정의되지 않은 상태로 남는다.
- **무엇을 했나**: `moveit_resources_panda_moveit_config`(실제로 동작하는 ROS2 Jazzy 레퍼런스 패키지)의 `ompl_planning.yaml`을 참고하여 파일 최상단에 다음 3개 키를 추가:
  ```yaml
  planning_plugins:
    - ompl_interface/OMPLPlanner
  request_adapters:
    - default_planning_request_adapters/ResolveConstraintFrames
    - default_planning_request_adapters/ValidateWorkspaceBounds
    - default_planning_request_adapters/CheckStartStateBounds
    - default_planning_request_adapters/CheckStartStateCollision
  response_adapters:
    - default_planning_response_adapters/AddTimeOptimalParameterization
    - default_planning_response_adapters/ValidateSolution
    - default_planning_response_adapters/DisplayMotionPath
  ```
- **왜 이렇게 해야 하나**: MoveIt2는 "요청 전처리(request adapters) → 실제 플래너 실행(planning plugin) → 응답 후처리(response adapters)"의 3단계 파이프라인을 노드 하나(`move_group`)가 전부 yaml에서 읽어서 구성한다. ROS1처럼 launch 파일에 흩어놓는 방식이 아니므로, 파이프라인별 yaml 파일 하나에 이 3가지가 다 있어야 파이프라인 자체가 성립한다.

### 3.3 버그 3 — 가속도 제한 없음 → 궤적 시간 파라미터화 실패

- **증상**: 버그 1, 2를 고친 뒤에는 `move_group`이 정상 기동하고("You can start planning now!") RViz도 뜨지만, **RViz에서 "Plan & Execute"를 누르면 항상 실패**함.
  ```
  [ERROR] [...time_optimal_trajectory_generation]: No acceleration limit was defined for joint joint_1! You have to define acceleration limits in the URDF or joint_limits.yaml
  [ERROR] [...add_time_optimal_parameterization]: Response adapter 'AddTimeOptimalParameterization' failed to generate a trajectory.
  [ERROR] [move_group]: PlanningResponseAdapter 'AddTimeOptimalParameterization' failed with error code FAILURE
  ```
  RViz에는 `MoveGroupInterface::move() failed or timeout reached`로 표시됨.
- **왜 발생했나**: 원본 ROS1 설정은 `has_acceleration_limits: false`였다. ROS1/MoveIt1의 기본 시간 파라미터화 알고리즘(`IterativeParabolicTimeParameterization`)은 가속도 제한이 없어도 동작했지만, **MoveIt2의 기본 응답 어댑터인 TOTG(Time-Optimal Trajectory Generation, `AddTimeOptimalParameterization`)는 가속도 제한이 반드시 있어야** 궤적의 시간 배분을 계산할 수 있다. 즉 "경로(path)는 성공적으로 찾았지만, 그 경로를 실제 실행 가능한 시간 궤적(trajectory)으로 변환하는 마지막 단계에서 실패"한 것.
- **무엇을 했나**: `joint_limits.yaml`의 6개 조인트 전부 `has_acceleration_limits: false` → `true`, `max_acceleration: 0.0` → `100.0`으로 변경.
- **왜 이렇게 해야 하나**: URDF 자체에는 가속도 한계가 정의되어 있지 않은 로봇이었기 때문에(속도 한계만 `<limit effort="100" velocity="100"/>` 형태로 있었음), MoveIt이 궤적을 시간 스케일링할 근거 값이 필요하다. 정확한 실제 로봇 사양값이 없는 상태이므로, 우선 "테스트가 가능한" 임의의 값(속도와 동일한 100)을 넣어 파이프라인을 통과시킴 — **실제 로봇(하드웨어)에 연결하기 전에는 반드시 Hanwha 공식 사양서의 실제 가속도 한계값으로 교체해야 함** (아래 5장 참고).

이 3가지를 모두 고친 뒤 `colcon build` → 재실행 → RViz의 인터랙티브 마커로 목표 자세를 잡고 "Plan & Execute"를 눌렀을 때, 그리고 `moveit_py`로 작성한 자동 검증 스크립트(무작위 관절 목표로 planning + execution)로도 `PLAN_SUCCESS: True`, `Completed trajectory execution with status SUCCEEDED`를 확인함.

### 3.4 문제 4 (설정 버그 아님) — 데모를 두 번 동시에 실행해서 생긴 충돌

- **증상**: 버그 1~3을 다 고친 뒤에도, 사용자가 터미널에서 `ros2 launch hcr_moveit_config demo.launch.py`를 직접 실행했을 때 컨트롤러 스포너가 `Controller already loaded, skipping load_controller` → `Could not configure controller ... no controller with this name exists`로 실패하고, RViz에서는 `unknown goal response, ignoring...` / `unknown result response, ignoring...`와 함께 Plan & Execute가 "aborted"로 표시됨. 그런데 로그를 자세히 보면 실제 궤적 실행 자체는 `Completed trajectory execution with status SUCCEEDED`로 끝나 있었음 — 즉 팔은 실제로 움직였는데 UI만 실패로 표시됨.
- **왜 발생했나**: 검증 과정에서 Claude가 백그라운드로 `demo.launch.py`를 이미 띄워둔 상태였는데, 사용자가 이를 모르고 동일한 launch를 한 번 더 실행함. 그 결과 `move_group`, `rviz2`, `ros2_control_node`, `robot_state_publisher`, `static_transform_publisher`가 **각각 2개씩 동시에 실행**되었고, 네임스페이스 분리 없이 동일한 토픽/서비스/액션 이름(`/controller_manager/*`, `/move_action` 등)을 두 세트의 노드가 동시에 사용하면서 충돌. 특히 액션 클라이언트(RViz)가 자신이 보내지 않은 goal에 대한 응답(다른 인스턴스로 온 응답)을 받아 goal ID가 안 맞는 상황이 발생 → 클라이언트 입장에서는 "내가 기다리던 응답이 아니다" → timeout/aborted로 처리. 반면 컨트롤러(리소스는 하나만 존재)는 실제로 명령을 받아 정상 실행했기 때문에 로그상 SUCCEEDED가 남음.
- **무엇을 했나**: 두 세대의 프로세스를 전부 `kill -9`로 정리하고, 이후로는 **하나의 launch만 실행**하도록 정리. 특히 Claude가 백그라운드로 띄우고 사용자가 모른 채 다시 띄우는 상황을 피하기 위해, 이후로는 사용자가 자기 터미널에서 직접 `ros2 launch`를 실행하고 `Ctrl+C`로 직접 끄는 방식으로 합의함.
- **왜 이렇게 해야 하나**: ROS2의 토픽/서비스/액션은 기본적으로 프로세스 간 전역 이름공간을 공유한다. 같은 이름의 노드/컨트롤러 매니저를 네임스페이스 분리 없이 두 번 띄우면 "어느 쪽이 진짜 서버인지" 클라이언트도 서버도 알 수 없는 상태가 되므로, **동일 launch를 중복 실행하지 않는 것**이 근본적인 예방책이다 (동시에 두 개를 띄우고 싶다면 `-r __ns:=...` 같은 네임스페이스 분리가 필요하지만, 이번 목적에서는 불필요).

## 5. 향후 참고 사항 (다른 HCR 모델이나 다른 로봇을 포팅할 때)

1. **저장소 전체가 ROS1인지부터 확인**: `CMakeLists.txt`의 `find_package(catkin ...)`, `package.xml`의 `<buildtool_depend>catkin</buildtool_depend>`, `launch/*.launch`(XML, `.launch.py` 아님) 셋 중 하나라도 있으면 ROS1 산출물이라고 보면 된다.
2. **description 패키지(URDF/mesh만 있는 패키지)는 변환이 쉽다** — `ament_cmake`로 CMakeLists/package.xml만 바꾸면 대부분 끝난다. 이번처럼 코드가 없고 URDF/mesh/launch만 있는 경우 특히 그렇다.
3. **MoveIt1 Setup Assistant 산출물(`xxx_moveit`)은 새로 만드는 게 낫다** — 파일명 패턴(`fake_controllers.yaml`, `ros_controllers.yaml`, `setup_assistant.launch` 등)이 있으면 한 줄씩 포팅하기보다, `moveit_resources_panda_moveit_config` 같은 **ROS2 Jazzy 레퍼런스 패키지의 디렉토리 구조를 그대로 베끼고** SRDF/kinematics.yaml/joint_limits.yaml/*_planning.yaml만 기존 값에서 재사용하는 편이 훨씬 빠르고 정확하다.
4. **재사용 가능한 것 / 새로 써야 하는 것**:
   - 그대로 재사용 가능: SRDF(그룹/그룹스테이트/충돌비활성화 부분), kinematics.yaml
   - 재사용하되 검증 필요: joint_limits.yaml(타입/가속도), `*_planning.yaml`(플러그인 키 추가)
   - 반드시 새로 작성: `*.launch` → `*.launch.py`, `ros_controllers.yaml`/`fake_controllers.yaml` → `ros2_controllers.yaml`+`moveit_controllers.yaml`, URDF에 `ros2_control` 태그 추가
5. **가속도 한계값은 실제 로봇 스펙으로 교체할 것**: 이번 작업의 `max_acceleration: 100.0`은 파이프라인을 통과시키기 위한 임시값이다. 실기 연동 전 Hanwha HCR-5 공식 사양서의 조인트별 최대 가속도로 반드시 교체해야 한다. 같은 이유로 `max_velocity: 100.0`(rad/s)도 비현실적으로 큰 값이라 실기 사용 전 재검토가 필요하다.
6. **디버깅은 항상 "설정 로딩 → 로직" 순서로 접근**: 이번 3개 버그가 전부 "move_group이 뜨자마자/처음 plan 시도할 때 죽는다"는 동일 패턴이었다. yaml 파싱·타입 문제, 파이프라인 플러그인 키 누락, 궤적 파라미터화 요구값 누락처럼 **"설정 파일이 요구 스키마를 만족하는가"**를 하나씩 지워나가는 게 가장 빠르다.
7. **launch는 한 번에 하나만**: 백그라운드 검증용으로 띄운 launch가 있다면 반드시 종료 후 사용자가 재실행하거나, 애초에 한쪽만 띄우기로 합의할 것 (3.4절 참고).
