# ros2_control 하드웨어 인터페이스 구성 — 중간결과물 (260809 산국·매발톱·동백·수련 / 260811-버스바 — B 실기 읽기 / 260811-오일리스부싱 — 결함 ① 수정·C 착수분)

**대상**: 플러그인 `hcr_bridge/HcrSystemInterface` **(신설 완료)** · `markch/hcr5_ros2` · 검증환경 09pc ·
컨테이너 `moveit2_dev:jazzy`(ros2_control **4.45.2**)

> **채운 순서와 주체** — ① 계약을 구현 전에 문서만으로 고정(**산국**, Mark 지시) → ② 병렬 3분할로 구현·실측:
> **매발톱**(S2, xacro·launch·mock 회귀) · **동백**(S3, 실기 읽기 전용 계측) · **수련**(S1, 플러그인 구현·병합).
> **원 계약 문장은 지우지 않았다** — 실측이 계약과 어긋나는 곳은 계약을 남긴 채 나란히 적었다.
>
> ⚠️ **실기 대면은 B(읽기) + C 착수분까지 닫혔고 C 본체(쓰기)가 남았다** (260811-버스바·오일리스부싱, 04pc — §3-B·§3-C).
> `on_activate`·`read`·`on_deactivate`·`on_cleanup` 은 실기에서 **돌았다**. **`write` 의 발행 경로만 아직 한 번도 안 돌았다** —
> 그것만 `allow_motion:=true` + 서보 ON 을 요구한다.
> B 가 찾은 **결함 3건 중 ①(`on_activate` 경합)은 수정·실측 완료**(§3-C). ②③ 은 설계 판정 대기 그대로다.

## 결론 (≤2줄, 서술)
ros2_control **4.45.2**(Jazzy)가 하드웨어 컴포넌트별 `rw_rate`·`is_async` 를 지원하므로, 08-05 에 `SystemInterface` 를 기각한 세 근거 중 **주기 불일치(29.1Hz↔100Hz)는 구조적으로 해소된다**(사실 — 컨테이너에서 XML 속성·`HardwareInfo` 필드 확인, S2 가 mock 으로 `rw_rate=30`·`is_async=true` 를 실제로 세워 재확인).
그래서 **모드 2종을 다 구현한다**(계획) — ① 실기 없이 도는 **mock**(명령 루프백, **회귀 7/7 통과**) ② **실기를 실제로 움직이는 모드**(`HcrSystemInterface` + `allow_motion:=true` — **읽기 경로는 실기 실측 완료**(§3-B), **쓰기는 미검증**). 남은 두 기각 근거(자율주행 실행 모델 · 컨트롤러가 보간 소유)는 그대로여서 ②는 **점대점 한정**이고 연속 스트로크는 `program/plan` 에 남긴다(가설 — 실기 미검증).

**⚠️ 계약 전제가 사실과 달랐다 — `motion/joint/speed`** (S3 실측, 보고 의무 항목).
발행된다. **9.82Hz**(평균 101.88ms, SD 4.30ms) 로 position 의 **≈1/3 주기**이고, 관절 키 6개·봉투가 position 과 **동일**하다.
정지 상태 값이 35초 내내 고정이고 base 만 정확히 `0`, 나머지는 인코더 1~3.5카운트 상당의 **양수** — **단위·부호 미상**(업무목록 **T19**).
→ **판정: 계약대로 차분을 유지한다**(Mark·S1). 근거 둘 — ① 차분 품질이 이미 확인됐다(정지 구간 **정확히 0.0000 rad/s**, 1024표본, 관절값 SD **0.000000°**) ② speed 를 채택하면 velocity state 갱신이 **1/3 로 느려진다**. 단위·부호가 밝혀지면 재검토한다.

**`velocity` state 는 실기 원천이 없는 산출값이다**(사실). 안 채우면 JTC 가 0/NaN 을 피드백으로 쓰고, 부정확하면
허용오차 위반이 헛나온다 — 산출 품질이 안 나오면 이 행과 그 파일의 `state_interfaces` 를 **같이 줄이는 게 정직하다**.

## 2. 주기·정합 (행 = 주기원 1건 — 이 로봇의 핵심 쟁점)
| 주기원 | 값 | 근거 | read()/write() 처리 |
|---|---|---|---|
| controller_manager update_rate | **100Hz** → **B 실측 100.01Hz** (컨트롤러 2종 periodicity 평균, SD 0.87·1.22) | 설정 (`ros2_controllers.yaml:4`) · B 실측 | 손대지 않는다 — 하드웨어 주기를 `rw_rate` 로 분리한다. **분리가 실기에서 성립했다**(아래) |
| 실기 상태 버스 | **29.1Hz** (주기 **34.4ms**) → **29.21·29.26Hz** (S3) → **B 실측 29.10Hz** (04pc, 최대 간격 **71.14ms**) | 실측 (hcr_comm README §5.2 · S3 35s×2회 · B 15s) | `<ros2_control … rw_rate="30">`. MQTT 콜백이 캐시에 쓰고 `read()` 는 **캐시 복사만** — 블로킹 없음 (**실행시간 평균 54.9µs** 로 확인) |
| **`read()`/`write()` 실효 주기** | **33.33Hz** — 요청한 `rw_rate=30` 이 **아니다**(+11.1%) | **B 실측** (`/controller_manager/statistics/full`, 표본 9454) | 100/3 = 33.33 에 정확히 맞는다 → CM 이 `update_rate` 격자에 **정수 분주로 스냅**한 것(가설). min 26.24 / max 34.51Hz 는 3~4주기 지터 |
| 명령 RPC 왕복(ack) | **115~137ms** | 실측 (hcr_comm README §4) | `is_async="true"` **+ 플러그인 자체 워커 스레드**. 동기 `pubWithAck` 를 `write()` 안에서 부르면 100Hz 루프가 **최대 13.7주기** 멈춘다 |
| 궤적 보간 소유자 | 점대점 = **JTC** / 연속 스트로크 = **로봇 컨트롤러** | 설계 | `write()` 는 점대점 목표만 낸다. 스트로크는 `program/plan` — **이 계약 밖**(hcr_bridge README §5) |

`rw_rate`·`is_async` 는 `<ros2_control>` 태그 **속성**이고 세부는 `<properties><async …/></properties>` 다 —
컨테이너의 `ros2_control_test_assets/descriptions.hpp:818-897` 에서 확인(사실).

**주기 관련 실측 3건 (전부 사실)**
- **`rw_rate="30"` 정당** — 실측 29.2Hz 는 30Hz 와 **2.6% 차**(S3).
- **`read()` 무수신 타임아웃 1.0s 는 헛발동하지 않는다** — 최대 수신 간격 **75.33ms** 대비 **13.3배** 여유. 단 **100ms 이하로 조이면 헛발동한다**(S3).
- **CM 은 100/30 비정수배를 거부하지 않는다** — S2 가 mock 으로 세워 확인. `list_hardware_components` 가 `read/write rate: 30 Hz`·`is_async: True` 를 직접 찍고, `is_async` 는 *"Starting async handler…"* 로그로 **속성값이 실제로 읽힌 것**이 확인된다.
- **V-6 은 절반만 닫혔다** — *구조적 거부가 없다*는 확인됐고(사실), *실기에서 그 불일치가 기능적으로 문제되는가*(낡은 표본을 JTC 가 어떻게 받는가)는 **여전히 미검증**(B3).

**`is_async`·`rw_rate` 파서 함정 2건** (S2, 사실) — `parse_bool` 은 **대소문자 무관**이라 xacro 가 내는 `"True"`/`"False"` 를 그대로 받지만 **`1`·`0`·빈 문자열은 예외를 던진다**. `rw_rate` 는 **양의 정수만** 받는다 — 기본값을 `0` 으로 두면 안 뜬다.

|---|---|---|---|
| ① 무응답 호스트 | `192.168.0.99:1883` | **3.004s** | "브로커에 TCP 로 닿지 않는다" |

①이 **3초에 끊기는 것이 설계 요점**이다 — `mosquitto_connect` 는 블로킹이고 취소가 안 돼 무응답 호스트에서 OS 기본 타임아웃(수십 초~2분)에 잡힌다. 그래서 그 앞에 **시간 상한을 건 TCP 프로브**를 둔다(`hcr_system_interface.cpp` `tcpProbe`).

⚠️ **그 뒤 controller_manager 가 프로세스째 abort 한다**(사실) — `Failed to set the initial state of the component … to active` → `std::runtime_error` → SIGABRT + 스택트레이스. **플러그인은 계약대로 ERROR 를 반환했고 abort 는 프레임워크 거동이다.** 실기 없이 실기 모드를 띄우면 데모가 통째로 죽는다는 뜻이라, 기동 절차에 영향이 있다. 완화 후보 파라미터 `hardware_components_initial_state.{unconfigured,shutdown_on_initial_state_failure}` 는 **효력이 확인됐다**(260811-진공펌프, V-12 통과 — 2종 다 듣는다. `shutdown_on_initial_state_failure:false` 는 configure 를 시도하되 throw 하지 않고, `unconfigured:[hcr_robot_system]` 은 configure 자체를 건너뛴다. 둘 다 `hardware_components_initial_state.` **하위**다).

## 3-B. B — 실기 읽기 실측 (260811-버스바, 04pc) ★

**`on_activate`·`read` 가 실기에서 처음 돌았다.** 기동 = `hardware_plugin:=hcr_bridge/HcrSystemInterface rw_rate:=30 is_async:=true`,
`allow_motion` 기본 `false`, 서보 **OFF**, 축온 **48°C**(종료 시 **+0** — *B 는 발열을 안 쓴다*는 전제가 실측됐다).

| 확인 | 기준 | 실측 | 판정 |
|---|---|---|---|
| B1 컴포넌트·인터페이스·컨트롤러 | 1개 active · 30Hz · `is_async` · 6/6/6 · 컨트롤러 2 | 전부 일치. `read/write rate: 30 Hz`·`is_async: True` 가 직접 출력된다 | **통과** |
| B2 상태 정합 ★ | 정답지 ↔ `/joint_states` | 코드 출력 ↔ 독립 구독기 변환이 **6/6 일치, 최대 편차 3e-21 rad**(double ULP) | **부분** — 아래 |

### 이 구간이 찾아낸 결함 3건 (전부 사실 — mock 에서는 안 나온다)

**① `on_activate` 가 확률적으로 실패한다 — 경합. ✅ 수정·실측 완료 (260811-오일리스부싱 → §3-C)**
`on_configure` 는 `fieldbus_ok_` 를 `false` 로 리셋하고(`hcr_system_interface.cpp:205`) **`motion/joint/position` 첫 표본만** 기다린다(252-256행).
그런데 `on_activate` 는 `fieldbus_ok_` 를 **즉시** 요구한다(268행). 그 플래그는 `status/operation` 이 와야 서는데 그 토픽 주기가 **51.5ms** 다.
→ **configure→activate 간격이 51.5ms 보다 짧으면 반드시 실패한다.**
- 최초 기동은 간격 **47ms** 로 통과했다 — **운이다**
- `set_hardware_component_state … active` 로 재활성하면 간격이 **1ms 미만** → **3/3 전부 실패**
- 그래서 **통신 두절에서 복구할 길이 없다. 프로세스 재기동뿐이다.** (`publish_permanently_locked_` 때문이 **아니다** — 그것은 328-329행에서 경고만 내고 SUCCESS 로 지나간다)
- **메시지가 자기모순이라 진단을 막는다** — `last_fieldbus_`(헤더 120행)는 리셋되지 않아
  *"필드버스가 FIELD_BUS_SW_STATE_CONNECTED 가 아니다 (현재 'FIELD_BUS_SW_STATE_CONNECTED')"* 가 찍힌다
- ~~고치는 방향(가설)~~ → **채택안 = 후자**: `on_activate` 가 `fieldbus_ok_` 를 **500ms 상한으로 대기**하고, `on_configure` 가 `last_fieldbus_` 를 리셋한다. `on_configure` 를 안 건드린 이유는 **A3/V-11 의 3경로 타이밍을 보존**하기 위해서다(그 경로들은 `on_activate` 에 도달하지 않는다). 실측은 §3-C

**② `rw_rate=30` 이 30Hz 로 돌지 않는다 — 실효 33.33Hz. 다만 기능적으로는 문제없다**
V-6 이 물은 *"100/30 비정수배가 기능적으로 문제되는가"* 에 답이 나왔다. 구조적 거부가 없고(S2), **기능적으로도 문제되지 않는다** —
`LoanedStateInterface joint_1/position` 기준 **timeout 2건(0.0012%) · missed call 1605건(0.9912%) / 161922 호출**.
버스(29.10Hz)보다 `read` 가 **빨라서** 표본을 놓치지 않는 방향이라 안전하다. 다만 **요청한 주기가 그대로 실현되지는 않는다.**

**③ `allow_motion=false` 여도 실기에 명령이 나간다 — `move/stop`**
`on_error` 의 `move/stop` 경로는 `allow_motion_` 을 **보지 않는다**(341·362-368행). B4 뒤 재활성 시도에서 **링크가 복구된 상태로 3회 발행**돼
실기 `robotState` 가 `ROBOT_STATE_IDLE` → **`ROBOT_STATE_STOPPED`** 로 바뀌었다. 설계대로이고 서보 OFF·정지 중이라 무해했지만,
**"읽기 전용 모드"가 실기 무발행이라는 뜻은 아니다.** S3 는 publish **0건**이었으나 이 구간은 **publish 가 있었다.**

## 3-C. C 착수분 — 결함 ① 수정 · 안전 게이트 실증 (260811-오일리스부싱, 04pc) ★

**설계 메모 2건**
- **데드밴드와 최종값의 관계** — 데드밴드는 *목표가 움직이는 동안*만 건다. 목표가 멎으면(직전 주기와 같으면) 데드밴드와 무관하게 **최종값을 전정밀도로 1회** 낸다. 안 그러면 궤적 끝에서 데드밴드만큼 못 미친 자리에 선다.
- **ack 없으면 보냈다고 치지 않는다** — 워커는 `pubWithAck` 응답이 있을 때만 `last_sent` 를 갱신한다. 그래야 다음 목표가 데드밴드에 먹히지 않는다.

**동시 접속 중재는 게이트로 두지 않는다 — 전제다**(Mark, 260809). 컨트롤러 랜선을 **PC 1대에만** 물리므로 실기
쓰기 주체가 구조적으로 하나다. 브로커는 무인증·무중재라 이건 소프트웨어가 아니라 **배선이 지키는 전제**이며,
허브를 끼우거나 실기 모드를 여러 PC에 배포하면 그 순간 깨진다(이미지를 공유해도 원격 PC 는 mock 만 쓸 수 있다).
