## 2. 기동 · 지령 · 정지

명령의 **성격이 셋으로 갈린다.** 창 배치가 그 성격을 따른다 — 편의가 아니라 구조다.

| | 성격 | 수명 | 하는 일 | 실패하면 |
|---|---|---|---|---|
| **기동** (bringup) | **상주** — 창을 점유한다 | 창이 사는 동안 | 로봇을 ROS 제어 **아래로 넘긴다**. 라이프사이클 `unconfigured→configured→active`, 명령 인터페이스를 **claim** (검증 V-3) | 아무것도 못 한다 |
| **지령** (command) | **일회** — 붙었다 뜬다 | 수 초 | 선 계에 **액션 goal 하나**를 얹는다 | 그 goal 만 실패, 계는 산다 |
| **정지** (shutdown) | 한 번 | — | 기동이 만든 상태를 **되돌린다** (`on_deactivate`) | ⚠️ **서보가 남는다** |

**지령을 백 번 해도 기동 상태는 안 바뀐다.** 반대로 기동을 다시 하면 지령이 하던 것이 끊긴다.

### 창 배치

| **3** | 지령 | 아무 창에서 몇 번이든 — 여기가 자유롭다 |

### 2-A. 기동 — 창 1

```bash
ros2 launch hcr5_bridge bringup.launch.py real:=true allow_motion:=true
```

**`move_group` 을 안 띄운다.** MoveIt 없이 `controller_manager` · `robot_state_publisher` ·
컨트롤러 2개 · RViz2 만 선다. 그것이 이 launch 의 요점이다(README §0 '차이').

| 모드 | 인자 | 로봇 |
|---|---|---|
| sim (mock) | 없음 | 안 움직임 · **실기 불필요** |
| 실기 읽기 | `real:=true` | 안 움직임 |
| 실기 쓰기 | `real:=true allow_motion:=true` | **움직인다 — e-stop 대기 필수** |

`use_rviz:=false` 로 RViz2 를, `auto_servo:=false` 로 서보 자동화를 끈다.

**이 순서로 나와야 한다** — 하나라도 빠지면 멈춘다:

```
Configured and activated joint_state_broadcaster
Configured and activated hcr_arm_controller
활성화 — 명령 버퍼 = 실기 [...]°          ← 플러그인이 실기를 잡았다
서보 ON — ack 수신
```

그리고 **RViz2 창에 로봇 자세**가 뜬다.

> **서보 ON 이 컨트롤러 활성 *뒤*인 것이 안전 설계다.** `on_activate` 가 `get/command/pos` 로
> 명령 버퍼를 **현재 실기 자세로 채우므로**(`hcr_system_interface.cpp:306-330`), 기동 직후 자동 발행되는
> `move/joint/here` 2건이 현재 자세 그대로다 — 로봇이 안 움직인다. 순서가 뒤집히면 그 보장이 깨진다(§5 함정 ⑤).

### 2-C. 지령 — 창 3

목표는 **URDF rad** 로 준다. 실기 도(度)와의 대응은 규약 변환(README §1)을 거친 값이다.
**숫자를 넣기 전에 아래 두 환산을 반드시 거친다** — 여기서 어긋난 사고가 §5 함정 ⑧ 이다.

#### 단위 — 넣는 숫자는 URDF **라디안**이다

`FollowJointTrajectory.positions` 는 ROS 표준 SI 라 rad 이고, 그 rad 는 **URDF 좌표계** 기준이라
실기 도(度)와 한 겹 더 어긋나 있다. **두 겹을 한꺼번에** 넘겨야 한다.

```
실기 도 → 넣을 값(rad) :  q_URDF = (SIGN·q_실기 + DELTA) × π/180
넣을 값(rad) → 실기 도 :  q_실기 = (q_URDF × 180/π − DELTA) / SIGN
```

| | joint_1 | joint_2 | joint_3 | joint_4 | joint_5 | joint_6 |
|---|---|---|---|---|---|---|
| SIGN | +1 | +1 | **−1** | +1 | +1 | +1 |
| DELTA (도) | **90** | **90** | 0 | **90** | 0 | 0 |

근거는 `include/hcr5_bridge/joint_convention.hpp` 다. joint_1 만 펴서 적으면 —

| 넣는 값 (rad) | URDF 도 | **실기 도** | |
|---|---|---|---|
| `1.570796` | 90° | **0°** | 홈 |
| `1.745329` | 100° | **10°** | P1 |
| `1.919862` | 110° | **20°** | P2 |
| `15` | 859.44° | **769.44°** | ← 2.1 바퀴. §5 함정 ⑧ |

⚠️ **실기 도를 그대로 넣으면 안 된다.** `15` 는 15° 가 아니라 15 rad 다. joint_1 을 실기 X° 로
보내려면 `(X + 90) × π/180` 을 넣는다 — 실기 15° 는 `1.832596` 이다.

#### 속도 — `time_from_start` 가 곧 속도다

goal 에 `velocities` 를 안 주면 JTC 의 `splines` 가 **선형 보간**으로 떨어져 **등속**이 된다.
그래서 속도는 이 한 줄로 정해진다:

```
속도(도/s) = |목표 − 현재| (실기 도) ÷ time_from_start (초)
```

#### 각속도인가 선속도인가 — **층이 다르다** ★

`--speed` 는 **각속도**(실기 도/s)다. `movej` 가 관절 공간이라 그렇다.
**선속도(mm/s)는 이 경로에 없다.**

| 층 | 속도를 정하는 것 | 단위 | 우리 경로인가 |
|---|---|---|---|
| **JTC 액션** (ros2_control) | `time_from_start` **하나뿐** | 관절 도/s (**각속도**) | ✅ **지금 이것** |
| `move/joint/here` (MQTT 직결) | 실기가 자율주행 · `set/velocity` 0~1 배율 | 실측 9.7°/s | 하드웨어가 소유 |
| `program/plan` `joint` | 노드 velocity (기본 50) | 도 계열 (**각속도**) | ❌ 다른 층 |
| `program/plan` `linear` | 노드 velocity (기본 500) | **mm/s (선속도)** | ❌ 다른 층 |
| MoveIt 속도 스케일 | `velocity_scaling_factor` | 배율 | ❌ moveit2 를 뺐다 |

- **`FollowJointTrajectory` 에는 선속도라는 개념이 없다** — 관절 위치와 시간뿐이다
- `move/joint/here` 에도 속도 인자가 없다 — 전역 `set/velocity` 배율만 있다
- 선속도/각속도 구분은 **실재하지만 `program/plan` 층의 것**이다 (`hcr5_mqtt/README.md` §6.1.1)

#### 실행기에 속도를 주는 법

| 주는 방식 | 인자 | 뜻 |
|---|---|---|
| 속도로 | `--speed D` | D°/s 로 가라 → 시간 자동 계산 |
| 시간으로 | `--sec N` | N초에 가라 → 속도는 그 결과 |
| (생략) | — | **2°/s** |

**속도 기준은 「가장 많이 도는 축」이다.** P2 는 base 10° · wrist3 20° 라 **wrist3 가 기준** — `--speed 2` 면 10초다.

| `--speed` | P1(10°) 소요 | 출처 |
|---|---|---|
| `1` | 10초 | 검C2 창 실측 1.25°/s 보다 느리다 |
| **생략 = 2** | 5초 | 기본값 |
| `5` | 2초 | 눈으로 빠르다고 느껴지는 선 |
| `10` | 1초 | **상한** — 여기까지 `--force` 없이 통과 |
| 180 | — | HCR-5 공식 최대 (Appendix G) |

**상한 10°/s 의 근거** — 실기 자율주행 실측이 **9.7°/s** 다. 그보다 빠른 명령은 실기가 못 따라와
명령 속도와 로봇 속도가 갈린다(§5 함정 ⑧). 넘기려면 `--max-speed 30 --speed 20` 또는 `--force` 를 **명시**한다.

#### 액션 직송에는 안전망이 없다 — 그래서 실행기가 게이트를 건다

| 안전망 | 액션 직송에 걸리나 | 이유 |
|---|---|---|
| **실행기 게이트 ①②③** | ✅ **걸린다** | 단위 표시 · `withinLimits()` · 속도 상한. **발행 전에** 건다 (2026-08-15 신설) |
| 관절한계 (실기 ±360° · J3 ±165°) | ✅ **걸린다** | 하드웨어 게이트 6 — `withinLimits()` 와 URDF 한계의 **이중 검사** (§5 함정 ⑨⑩) |
| MoveIt 속도 스케일 `0.1` | ❌ | planning 을 안 거친다. `/move_action` 경로(§6)에만 붙는다 |
| `joint_limits.yaml` 180°/s | ❌ | MoveIt 계획용이라 JTC 가 안 읽는다 |
| JTC `constraints` | ❌ | `ros2_controllers.yaml` 에 항목 자체가 없다 (§5 함정 ④) |
| `mqtt_cmd.py` 3중 가드 (`--max-delta 5°`) | ❌ | 그건 MQTT 직결 경로(§6)의 가드다 |

> 종전에는 이 표의 첫 행이 없어 *"계산이 곧 안전장치"* 였다. **그 계산이 사람 손에서 코드로 넘어왔다.**

| 점 | joint_1 | joint_2 | joint_3 | joint_4 | joint_5 | joint_6 | 실기 (도) | 비고 |
|---|---|---|---|---|---|---|---|---|
| **홈** | 1.570796 | 0 | 1.570796 | 0 | 1.570796 | 0 | `[0, −90, −90, −90, 90, 0]` | SRDF `hcr_home` |
| **P1** | **1.745329** | 0 | 1.570796 | 0 | 1.570796 | 0 | `[10, −90, −90, −90, 90, 0]` | base +10° |
| **P2** | **1.919862** | 0 | 1.570796 | 0 | 1.570796 | **0.349066** | `[20, −90, −90, −90, 90, 20]` | base +20° · wrist3 +20° |
| **1회전** | **7.853981** | 0 | 1.570796 | 0 | 1.570796 | 0 | `[360, −90, −90, −90, 90, 0]` | base 한 바퀴 — §5 함정 ⑨⑩ |

**base 한 바퀴**는 joint_1 한계를 실기 ±360° 에 정합시킨 뒤에야 된다(§5 함정 ⑨). 2026-08-15 실증은
**0° → 280° → 360° → 0°** 세 단계로 나눠 태웠다 — 종전 벽(270°)을 넘는지를 중간에서 확인하려던 것이다.
`7.853981` 은 **끝자리를 내린 값**이라 실기 359.99996° 에 선다(함정 ⑩). 단일 명령 `0° → 360°` 는 아직 안 태웠다.

**P1·P2 를 이 두 축으로만 잡은 이유** — 홈 자세에서 플랜지 높이가 **수학적으로 불변인 축은 joint_1(수직축 회전)과
joint_6(지금 아래를 향한 툴축 회전) 둘뿐**이다. 나머지 축(2·3·4·5)은 플랜지를 내릴 수 있어 작업대 클리어런스를
사람이 따로 확인해야 한다. 첫 수동 운전은 이 둘로만 한다.

#### 명령

```bash
ros2 run hcr5_bridge movej --deg 10 -90 -90 -90 90 0        # 홈 → P1
```
```bash
ros2 run hcr5_bridge movej --deg 20 -90 -90 -90 90 20       # P1 → P2
```
```bash
ros2 run hcr5_bridge movej home                             # P2 → 홈
```

한 줄씩, 앞 명령이 `← 종료 code=` 를 찍은 뒤 다음으로 간다. 겁나면 뒤에 **`--dry-run`** 을 붙여
계산만 먼저 본다 — 발행 없이 목표·현재·속도가 다 찍힌다.

**`--deg` 를 빼면 라디안이다.** `10` 을 그냥 넣으면 10 rad(실기 483°)로 읽힌다 — 게이트가 막지만,
막히는 것에 기대지 말고 단위를 맞춰 넣는다(§5 함정 ⑧).

`movel` 은 직교 목표를 준다 — **경로는 직선이 아니다**(§6).

```bash
ros2 run hcr5_bridge movel 489.909 -170.503 431.355 179.955 -0.001 -90.0 --dry-run
```

**속도는 `time_from_start` 가 정한다.** 위 명령들은 기본 **2°/s** — 검C2 창의 1.25°/s 보다 조금 빠르다.
플러그인 재발행 주기가 **ack 왕복 + 137ms ≈ 200ms** 라 이 속도면 한 스텝이 0.4° 다(중간결과물 §5).

### 2-D. 정지 — 창 1 에서 `Ctrl+C`

**하나로 끝난다.** 이 순서로 나오면 정상이다:

```
move/stop 발행 · 발행 잠금        ← on_deactivate
서보 OFF — ack 수신               ← launch 종료 훅
```

> **서보 OFF 자동화는 종전 설계를 뒤집은 것이다.** `on_deactivate` 주석이 *"서보는 끄지 않는다 —
> 브레이크 판단은 사람 몫"* 이라고 적는다. 바꾼 이유는 **서보를 켠 채 방치하는 쪽이 더 위험**하기 때문이다
> (§5 함정 ⑦, 58~61°C 6축 트립). 자세가 위험해 브레이크를 걸고 싶지 않으면 기동 때 `auto_servo:=false`.

⚠️ **`Ctrl+C` 없이 창을 닫으면(창 X 버튼·SSH 끊김) 어떻게 되는지 아직 확인 안 했다.** SIGHUP 에서
종료 훅이 도는지 미검증이다 — 서보가 켜진 채 남으면 함정 ⑦ 의 입구다. 확인 전까지는 **반드시 `Ctrl+C`** 로 끝낸다.

**남았는지 확인** ([`RUNTIME.md`](RUNTIME.md) §8):

```bash
docker exec moveit2_dev ps -ef | grep -E "ros2_control_node|robot_state_pub|rviz2" | grep -v grep
```

`bash -lc` 가 ROS 를 안 물고 오는 것(`ros2: command not found`)과 여러 줄 붙여넣기가 깨지는 것,
**둘 다 경계 사고**라 환경 문서가 원본을 든다. §0 진입만 지키면 이 문서 안에서는 안 밟는다.
아래는 그 자리에 있던 원문이다 — 호스트에서 한 줄로 쏠 때(§7) 여전히 유효하다.

**① `bash -lc` 는 ROS 환경을 안 물고 온다** (2026-08-15 03pc)
`docker exec moveit2_dev bash -lc "ros2 …"` → `bash: line 1: ros2: command not found`.
`.bashrc` 는 대화형 셸에서만 읽히기 때문이다. §7 의 명령들이 전부 `source /opt/ros/jazzy/setup.bash && source ~/ws_moveit2/install/setup.bash`
를 명시적으로 달고 있는 이유다. 대화형 `docker exec -it moveit2_dev bash` 는 그냥 된다 — **두 형태를 섞으면 되던 게 안 된다.**

**② 여러 줄을 통째로 붙여넣으면 깨진다**
블록 첫 줄이 `docker exec -it … bash` 면 새 셸이 열리고 **뒤따르는 줄들이 그 새 셸의 입력으로 빨려 들어간다.**
그래서 이 문서의 명령은 전부 **한 줄로 완결**되고 셸을 바꾸지 않는다. 함수 정의(`GO() { … }`)도 쓰지 않는다 —
정의는 그 셸에서만 살아서 창을 새로 열 때마다 다시 붙여넣어야 한다.

**③ `c1_tempwatch.py` 는 90초에 끊겼었다 — 2026-08-15 수정됨**
CONNECT 가 keepalive **60초**를 선언하는데 루프가 `recv` 만 해서 브로커가 1.5×60 = **90초**에 끊었다.
600초 창을 걸었다가 **89.15초**에 죽은 것이 발견 계기다(표본 870건 · 임계 위반 **0건** · 최고 **47°C**).
종전 창은 20~22초라 닿은 적이 없었다. 지금은 30초마다 PINGREQ 를 보낸다.
⚠️ 정상 종료 메시지 `✅ 창 종료 — **임계 미도달**` 은 *"임계에 안 닿았다"* 는 뜻이다 — 트립으로 오독하기 쉽다.

**④ `error_code: 0`(SUCCESSFUL)을 도착 판정으로 쓰면 안 된다**
JTC `constraints` 가 미설정이라(중간결과물 §3-D 발견 ④) 추종에 실패해도 성공이 나온다. 판정은 `mqtt_cmd.py pos` 로 한다.

**⑤ 기동 순간 `move/joint/here` 2건이 자동으로 나간다**
`allow_motion=true` 로 활성화하면 궤적을 안 줘도 발행된다(중간결과물 §3-D 발견 ⑦). 그래서 **①(launch) 먼저 → ③(서보 ON) 나중**이다.
서보가 꺼져 있으면 컨트롤러가 거부하므로 로봇은 안 움직인다.

**⑥ 종료할 때 `move_group` 이 exit −11(Segfault)로 죽는다 — 정상이다**
`MoveItCpp` 소멸자 문제로 검B·검C1 두 창 모두 그랬다. 종료 시점이라 무해하다.
다만 **고아 프로세스가 남을 수 있다** — 실제로 `robot_state_publisher`·`static_transform_publisher` 가 남은 사례가 있다.
재기동 전에 확인한다:
```bash
docker exec moveit2_dev ps -ef | grep -E "move_group|ros2_control_node|robot_state_pub|static_transform|rviz2" | grep -v grep
```

**⑦ 서보를 켠 채 오래 두지 마라**
2026-08-05 에 **58~61°C** 에서 6축 드라이브가 0.8초 만에 전부 트립했고 컨트롤러 재부팅으로만 복구됐다
(`hcr5_mqtt/README.md` §8 함정 3). 감시견의 58°C 즉시중단이 그 선이다.

**⑧ 넣는 숫자를 실기 도(度)로 착각하면 명령이 폭주한다 — `15` 가 명령 153.9°/s 였다** (2026-08-15 03pc)
홈(실기 0°)에서 `positions: [15, …]` · `sec: 5` 를 발행했다. `15` 는 15° 가 아니라
**15 rad = URDF 859.44° = 실기 769.44°** 로 해석됐고, 그걸 5초에 가라는 뜻이라 **명령 속도가 153.9°/s** —
④~⑥ 이 쓰는 2°/s 의 **77배**, 검C2 실측 1.25°/s 의 123배였다.
⚠️ **명령 속도 ≠ 로봇 속도다.** `move/joint/here` 는 목표를 주면 실기가 **자기 속도 프로파일로 자율 주행**한다
(실측 9.7°/s — `mqtt_cmd.py` 도움말). 명령이 그보다 빠르면 실기가 병목이라 로봇은 못 따라온다.
이 창은 실제 회전 속도를 계측하지 않았다 — **로봇이 153.9°/s 로 돌았다는 근거는 없다.** 반대로
`time_from_start` 를 넉넉히 주면 명령이 실기보다 느려져 그때는 명령이 속도를 정한다(④~⑥ 이 그 영역이다).
- 로봇은 **실기 267.77°** 에서 멈췄다. 명령이 URDF 한계 6.2832rad(= URDF 360° = **실기 270°**)에 닿아
  하드웨어 게이트 6 이 발행을 끊었기 때문이다 — 명령의 34.8% 지점이고, 멈춘 벽의 정체는 함정 ⑨ 다
- 로그는 `'joint_1' 목표 6.3247rad 가 URDF 한계 [-6.2832, 6.2832] 밖이다` **한 줄뿐**이다.
  `warned_limits_` 가 래치라 이후 차단은 조용하다 — **에러 1줄 = 사고 1건이 아니다**
- 그런데도 3.2초 뒤 `Goal reached, success!` 가 떴다 (함정 ④ 그대로다)
- 막아 준 안전망은 URDF 관절한계 **하나뿐**이었다. 나머지는 ④~⑥ "속도" 표대로 이 경로에 안 걸린다
- 목표값 역산이 15.07 로 나와 입력 `15` 와 일치한다(오차는 `rw_rate` 30Hz 양자화 1주기분).
  goal 에 `velocities` 가 없어 JTC `splines` 가 **선형**으로 떨어진 덕에 등속이라 역산이 가능했다

**⑨ URDF 관절한계가 실기 가동범위와 90° 어긋나 있었다 — j1·j2·j4** (2026-08-15 03pc 발견·수정·실증)
URDF 한계는 URDF 좌표에서 **대칭 ±360°** 였는데, 규약 오프셋 δ=90° 가 붙는 **j1·j2·j4** 는
그 대칭이 실기에서 깨진다. joint_1 로 보면 —

| | URDF | 실기 | 공식 ±360° 대비 |
|---|---|---|---|
| **종전** upper | +360° (`6.283185`) | **+270°** | **90° 좁다** ← 한 바퀴를 못 돌았다 |
| **종전** lower | −360° (`-6.283185`) | **−450°** | 90° 넓다 |
| **현행** upper | +449.99996° (`7.853981`) | **+359.99996°** | 정합 (함정 ⑩ 참조) |
| **현행** lower | −269.99994° (`-4.712388`) | **−359.99994°** | 정합 |

- 양(+) 방향으로 **한 바퀴가 안 됐다.** 함정 ⑧ 이 267.77° 에서 멈춘 벽이 바로 이것이다
- 음(−) 방향의 초과분은 `withinLimits()` 가 실기 ±360° 로 따로 막았다(이중 검사) — **안전엔 구멍이 없었다**
- j3(δ=0 · ±165°) · j5 · j6(δ=0 · ±360°) 는 δ=0 이라 어긋나지 않는다 — **고친 것은 j1·j2·j4 셋뿐**이다
- 고친 곳: `hcr_robot_description/urdf/hcr_robot.xacro` (팀 공용). ★ 2026-08-15 주석 참조
- **실증** (2026-08-15 03pc · 2°/s · 엔드이펙터 제거 상태): 홈 0° → 280° → 360° → 0° 완주.
  280° 에서 종전 벽 270° 통과 확인, 360° 지점 flange 가 **(489.941, −170.671, 441.500)** 로
  홈 (490.0, −170.5, 441.5) 과 일치 — 제자리 한 바퀴가 기하학적으로 확인됐다. 축온 최고 55°C

**⑩ 한계값 끝자리를 반올림하면 두 게이트가 싸운다** (2026-08-15 03pc 실측)
`write()` 는 한계를 **두 번** 본다 — `withinLimits()`(실기 도 ±360°)와 URDF `info_.limits`(rad).
**URDF 한계가 실기 한계보다 바깥이면**, URDF 검사는 통과하는데 실기 검사가 막는 상태가 된다.

```
정확한 450° = 7.853981633974483 rad
반올림 7.853982 rad → 실기 +360.000021°  → withinLimits() 차단
내림   7.853981 rad → 실기 +359.999964°  → 통과 (여유 0.000036°)
```

- 첫 수정 때 `7.853982`·`-4.712389` 를 넣었다가 **목표 360° 가 차단돼 359.98° 에 멈췄다.**
  로그는 `목표가 공식 가동범위 밖이다 (±360°, J3 ±165°)` 로 뜬다 — URDF 한계 메시지가 아니다
- 원칙: **URDF 한계는 실기 한계보다 항상 안쪽**으로 둔다. 끝자리는 올리지 말고 내린다
- 이 차단은 안전 설계대로 동작한 것이다. 고장이 아니라 **경계값을 잘못 쓴 쪽**이 문제였다

## 6. 다른 경로

| 하고 싶은 것 | 방법 |
|---|---|
| **직교 좌표로 이동** | `ros2 run hcr5_bridge movel <x y z rx ry rz>` — 로봇 IK 경유. ⚠️ **경로는 직선이 아니다** (시작·끝만 직교, 사이는 관절 보간) |
| **진짜 직선** | `program/plan` 의 `move.selected:"linear"` — 컨트롤러가 보간을 소유한다. 실측 직선 이탈 **0.045mm/179.3mm**. **ros2_control 을 안 탄다** (`hcr5_mqtt/README.md` §6) |
| MoveIt 계획·충돌검사를 태운 이동 | `hcr5_measurements/260812_T15검증/verify/c2_moveaction.sh <j1..j6> <scale>` — `/move_action` Plan&Execute. ⚠️ **`move_group` 이 필요하다** — `bringup.launch.py` 는 안 띄우므로 `hcr_moveit_config/demo.launch.py` 로 띄워야 한다 |
| 마커를 끌어서 대화형 | RViz MotionPlanning 패널 — 위와 같이 `move_group` 이 필요하다 |
| 계측까지 붙은 창 1회 | `verify/c2_run.sh {w1\|w2\|home}` — 계측기 3종 + 서보 사이클 + 원자료 회수 |
| ros2_control 안 쓰는 단발 이동 | `hcr5_mqtt/tools/mqtt_cmd.py movej <j1..j6>` — 3중 가드 내장, **실기 도(度)** 로 준다 |
| 연속 스트로크 | 이 계층 밖이다 — `program/plan` (`hcr5_mqtt/README.md` §6) |

## 7. 호스트에서 한 줄로 — 에이전트·스크립트용

창을 유지할 필요가 없다. 대신 `source` 를 매번 명시해야 한다(§5 함정 ①).
**사람이 로봇 앞에서 쓰는 방식은 §0~§2 다** — 이쪽은 재현·자동화용이다.

```bash
docker exec -d moveit2_dev bash -lc "source /opt/ros/jazzy/setup.bash && source ~/ws_moveit2/install/setup.bash && ros2 launch hcr5_bridge bringup.launch.py real:=true allow_motion:=true > /tmp/launch.log 2>&1"
```

```bash
docker exec moveit2_dev grep -E "Configured and activated|활성화 —|서보 ON|ERROR" /tmp/launch.log
```

```bash
docker exec moveit2_dev bash -lc "source /opt/ros/jazzy/setup.bash && source ~/ws_moveit2/install/setup.bash && ros2 run hcr5_bridge movej --deg 10 -90 -90 -90 90 0"
```

```bash
docker exec moveit2_dev pkill -INT -f "ros2 launch"
```

⚠️ **이 방식은 `Ctrl+C` 가 없다.** 서보 OFF 가 launch 종료 훅으로만 도므로, 내린 뒤 반드시 확인한다:

```bash
docker exec moveit2_dev bash -lc "cd ~/ws_moveit2 && python3 src/drivers/hcr5_mqtt/tools/mqtt_cmd.py pos"
```
