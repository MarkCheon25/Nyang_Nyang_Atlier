> **JTC 경로에서 `program/plan` 경로로 내린다.** 겹치는 근거(배타·발행순서·도착판정)는 여기서 다시 세우지 않고

> 없다는 것이 드러나 `movel` 과 함께 메웠다.

## 1. 주요기능

### 1.1 무엇을 하는가

```
ros2 run hcr5_bridge movej <j1> <j2> <j3> <j4> <j5> <j6> [옵션]
ros2 run hcr5_bridge movej home [옵션]
```

**관절값 6개를 주면 각 관절이 그 각도로 간다.** 엔드이펙터가 어떤 경로를 그리든 구속하지 않는다 —
`movel` 이 정확히 반대다(엔드이펙터를 구속하고 관절은 자유). 두 실행기는 **같은 층에서 서로 반대편**이다.

| | `movej` (이 문서) | `movel` ([movel.md](movel.md)) |
|---|---|---|
| 인자 | 관절각 6개 | 직교 좌표 x·y·z |
| 구속하는 것 | **관절 궤적** (각 축이 동시 시작·동시 도착) | 엔드이펙터 궤적 (직선) |
| 자유로운 것 | 플랜지 경로 — 일반적으로 **호(곡선)** | 관절 궤적 |
| 기준 좌표계 인자 | **없다** — 관절공간엔 원점이 없다 (§3.1) | `base`·`world`·`tool` |
| IK | 불필요 (관절값을 직접 받는다) | `robot/convertJointAngle` 필요 |
| FK | **필요** — waypoint 의 tcp·flange 칸을 채우려고 (§1.2) | 불필요 |

- **입력 단위는 기본 URDF 라디안**(ROS 표준 SI)이고 `--deg` 를 붙이면 실기 도(度)로 받는다. 근거는 §2.2.
- 어느 쪽이든 발행 전에 **두 단위를 다 찍는다** — README §3.8 단위 폭주 사고가 그 표가 없어서 났다.
- `home` 은 명명점이다 (`kHomeRealDeg` = 실기 도 `[0, −90, −90, −90, 90, 0]`).

### 1.2 경로 — `program/plan` 의 `joint` 노드

보간을 **컨트롤러가 소유한다.** movel 과 같은 문이고, `move.selected` 만 다르다.

```
1. get/command/pos        — 현재 자세. tcp·flange·joint 를 한 번에 준다
2. robot/convertPose ×2   — 목표 관절값의 FK. poseType tcp · flange 각각
3. program/clear
4. program/plan  — MOVE 노드 1개
     move.selected: "joint"
     waypoint.endPoint.fixed.{tcp, flange, joint}
5. program/play
6. program/end · event/motion 으로 도착 판정
```

**왜 FK 2회를 부르나** — 웨이포인트 한 칸이 `tcp`·`flange`·`joint` **세 표현을 동시에** 담고,
`hcr5_comm/README.md` §6.1.2 가 *"세 표현은 서로 정합해야 한다"* 고 못 박는다. 우리는 `joint` 만 알고 있으므로
나머지 둘을 FK 로 만들어 채운다. **관절공간 이동인데도 직교 좌표를 계산하는 이유가 이것뿐이다** —
경로 결정에는 전혀 쓰이지 않는다.

> `movel` 은 이 자리에서 `poseTriple()` 이 tcp·flange 에 **같은 pose 를 넣는다.** 그쪽은 `get/command/pos` 가
> 준 한쪽(기본 flange)만 쓰기 때문이다. TCP 오프셋이 0 이 아닌 세션에서는 어긋난다 — 업무목록 **L14** 와
> 같은 뿌리다. `movej` 는 FK 를 두 번 불러 **양쪽을 각각 정확히** 채운다. 이쪽이 옳고,
> movel 도 같은 방식으로 고칠 수 있다(§4 후속).

**노드 하나 = 구간 하나**이므로 현재 자세 → 목표 자세를 분할 없이 한 번에 간다.

⚠️ **`joint` 노드에는 `radius` 가 없다.** 블렌딩 반경은 `linear` 에만 있다
(`hcr5_comm/README.md` §6.1.1). 두산 `MoveJoint` 에는 radius 가 있으므로 이건 두 컨트롤러의 **차이**다 — §3.2.

### 1.3 배타 — ros2_control 스택과 동시에 못 쓴다

**근거는 [movel.md](movel.md) §1.3 이 원본이다.** `program/play` 는 컨트롤러가 자기 궤적을 실행하는 것이고
`bringup.launch.py` 는 `HcrSystemInterface` 가 명령 인터페이스를 claim 해 주기적으로 관절 지령을 쓴다.
둘이 동시에 돌면 명령이 부딪힌다.

→ 교체 후 `movej` 도 `servo`·`movel` 과 같이 **rclcpp 없이 도는 실행기**가 된다.

**이 교체로 첫째 칸이 빈다.** README:104 가 *"`movej` 만 첫째 칸에 남아 있다"* 고 적어 둔 그 칸이다.
이제 `hcr5_bridge` 의 운전 실행기 셋(`movej`·`movel`·`servo`)이 전부 MQTT 직결이고,
JTC 경로는 **MoveIt 이 쓰는 문**으로만 남는다.

| | 종전 movej (JTC) | **program/plan 경로 (이 문서의 movej)** |
|---|---|---|
| 진입 | `bringup.launch.py` 필요 | **스택 불필요** |
| 보간 소유 | JTC (관절공간) | **컨트롤러 (관절공간)** — 같은 공간, 다른 주체 |
| 현재 자세 조회 | ROS `/joint_states` | **MQTT `get/command/pos`** |
| 속도 지정 | `duration` 을 계산해 궤적점에 실음 | `move.joint.velocity` 를 노드에 실음 |
| 도착 판정 | **없다** — `error_code` 는 판정력이 없다(README §3.5) | **`program/end` · `event/motion`** + 자세 되읽기 |
| MoveIt·충돌검사 | 가능 | 없음 |

> **도착 판정이 생기는 것이 부수적 이득이 아니다.** 종전 movej 는 *"도착은 `mqtt_cmd.py pos` 로 본다"* 고
> 사람에게 떠넘겼다(`move_common.hpp:233`). 교체 후에는 실행기가 스스로 판정하고 오차까지 찍는다.
> Mark 가 *"이게 준비되어야 ros2 노드로 만들 수 있다"* 고 한 것이 이 지점이다 — 도착을 프로그램이
> 판정하지 못하면 그 위에 노드를 못 올린다.

> (2026-08-16 `get/command/pos`: rx 179.919 · ry −0.003 · rz −90.002).
> ZYX 확정은 잔차법으로 했으므로 **그 결론은 영향받지 않는다.** 인용만 틀렸다.

### 2.1 무엇을 원했나 (2026-08-16, Mark)

> 하면 좋겠어."

> "로봇암 내부의 어떤 토픽을 구독한 거거든. movej도 비슷한 방식으로 해보려 해."

> "**두산 로봇암의 movej와 유사한 방식으로 구현하려 해. 이게 준비되어야 ros2 노드로 만들 수 있다고 생각해.**"

세 문장이 셋을 결정했다 — **① MQTT 직결로 내린다 ② 두산의 `MoveJoint` 를 형(型)으로 삼는다
③ 이것이 최종물이 아니라 그 위에 올릴 ROS 2 노드의 토대다.**

③ 이 설계에 미친 영향이 크다. 사람이 터미널에서 치는 도구라면 도착 판정을 눈으로 해도 되지만,
**노드가 호출할 것이라면 도착을 프로그램이 판정해야 한다.** 그래서 `program/end`·`event/motion` 구독과
자세 되읽기가 선택이 아니라 필수 요건이 됐다 (§1.3 각주).

### 2.2 인자 규약은 현행 유지 — 기본 rad, `--deg` 로 실기 도

> Mark 판단 (2026-08-16): "현행 유지"

MQTT 경로의 네이티브 단위는 **도(度)** 다. 그러면 내부 변환을 없앨 수 있으니 도를 기본으로
뒤집는 선택지가 있었지만, 셋을 잃는다:

| 잃는 것 | 왜 |
|---|---|
| README §3.5 의 사용 예제 전부 | `movej 1.745329 0 1.570796 0 1.570796 0` 같은 줄이 전부 뜻이 바뀐다 |
| 팀 손버릇 | 과거 rad 명령을 그대로 치면 **에러 없이 엉뚱한 곳으로 간다** — 가장 위험한 실패 방식 |
| ROS 표준 SI 와의 정합 | ③ 의 ROS 2 노드는 rad 로 말한다. 실행기가 rad 를 모르면 그 층에서 또 변환해야 한다 |

→ 경계는 **실행기 안쪽**에 둔다. 밖으로는 rad 로 말하고, 안에서 `urdfRadToRealDeg()` 로 바꿔 MQTT 에 싣는다.
`joint_convention.hpp` 가 이미 그 변환의 원본이다.

⚠️ 이 변환을 빼먹으면 **로봇이 조용히 전혀 다른 자세로 간다** (`joint_convention.hpp` 머리주석).
그래서 발행 전에 rad·URDF도·실기도 **세 칸을 다 찍는다** — 종전 movej 의 `printTarget()` 이 하던 일이고,
rclcpp 를 떼면서도 이 표만은 그대로 가져왔다.

### 2.3 ✅ 닫힘 — `move.joint.velocity` 의 단위는 **도/s**

> **결론 (2026-08-16 실측 182점 · 6축 전부, 260816-호크니)**: `move.joint.velocity` = **도/s**,
> `acceleration` = **도/s²**. 지령 속도는 **오차 0.13% 로 그대로** 지켜진다. 다만 가감속이 사다리꼴이 아니다 —
> **`t = d/v + 1.54·(v/a) + 0.20초`** (RMS 잔차 0.037초, 최대 0.136초).
> **여섯 축이 모두 같은 모형을 따르고, 중력 방향도 시각도 무관하다 — 세 항 전부 상수다.**
> 아래는 그 블로커가 어떤 문제였고, **네 단계에 걸쳐** 어떻게 닫혔는지의 기록이다 — 2단계에서
> 1단계의 결론 하나를 폐기했고, 3단계에서 2단계의 정밀도 주장을 깎았고,
> **4단계에서 3단계의 "진짜 발견"이라던 것을 기각했다.**

#### 무엇이 문제였나

`hcr5_comm/README.md` §6.1.1 이 이렇게 적고 있었다 (**닫히기 전의 원문** — 지금은 갱신됐다):

> **기본값**: `joint` velocity 50 / acceleration 100, `linear` velocity 500 / acceleration 1000 / radius 0.
> (linear 단위는 mm/s·mm/s². **joint 는 도 계열 — 단위 표기는 미확정**)

**`linear` 는 mm/s 로 실측 확정**됐다 — movel 이 50 을 실어 정속 50.0mm/s 를 관측했다(movel.md §1.4).
`joint` 는 그 대조군이 없다. movel 착수 시점의 회전규약(🔴 → §2.3 에서 닫힘)과 **같은 자리의 구멍**이다.

**후보와 그 결과**:

| 가설 | velocity=2 이면 | 위험 |
|---|---|---|
| **도/s** (유력 → ✅ 확정) | 2°/s — 당시 movej 기본값과 같다 | 없음 |
| % 배율 | 컨트롤러 최대의 2% | 없음 — **더 느려진다** |
| rad/s | **114.6°/s** | 🔴 당시 상한 10°/s 의 11배 |

**도/s 가 유력한 근거 둘** (당시에는 가설, 실측으로 확인됨):
- `hcr5_comm/README.md` §4.1 이 *"각도·속도 단위 = 도"* 라고 명령 표 전체에 걸어 두었다
  (`jogJoint/start` 의 `speed:"45.00"`, `move/joint/home` 의 `velocity:"22.50"` 이 도/s 다).
- 두산 `movej` 의 `vel` 도 **deg/sec** 다 (§3.1). 두 컨트롤러가 같은 개념을 같은 이름으로 갖고 있으면
  단위도 같은 쪽에 걸린다 — movel.md §3.2 가 관찰한 그 공통 형태다.

#### ✅ 닫는 방법 — 실행기가 자기 가설을 스스로 잰다

회전규약처럼 **로봇을 안 움직이고** 가릴 방법은 없다. 속도는 움직여야만 관측된다.
대신 **첫 실행 한 번으로 확정되게** 만들었다 — 구현이 발행 직전에 사다리꼴 프로파일로 예상 소요시간을 찍고,
도착 후 실측 소요시간과의 **비율**을 함께 찍는다:

(⚠️ 아래 사다리꼴 식은 **당시의 예상 모형**이다. 2단계에서 램프 항이 `1.525·v/a` 로 갱신됐고
4단계에서 `1.54·v/a` 로 좁혀졌다. 코드도 그쪽으로 바뀌었다 — 이 블록은 1단계 기록으로 남긴다.)

```
예상 소요시간 t = d/v + v/a          (d = 최대 이동 축의 각변위, 사다리꼴 프로파일)

실측/예상 ≈ 1.0    → 도/s 확정
실측/예상 ≈ 1/57.3 → rad/s          (너무 빠르다 — 즉시 중단)
그 외              → % 배율 등. 비율 자체가 기준 속도를 알려준다
```

⚠️ **1번 축(base) 로 재지 마라.** 업무목록 L15 가 `joint_1` 이 359.999° 에 서 있던 사고를 적는다 —
한 바퀴를 되돌아가는 조건이 그 축에 붙어 있었다. `wrist2`(J5) 처럼 여유가 큰 축이 안전하다.

#### 1단계 실측 — 표본 하나로는 못 닫았다

한 번 재서 비율이 1.0 부근이면 끝날 줄 알았는데, 실제로는 **1.087** 이 나왔다. 8.7% 는 애매하다 —
도/s 가 맞는데 오버헤드가 낀 것일 수도, 환산계수가 0.92 인 배율 계열일 수도 있다. **표본 하나로는
그 둘이 구별되지 않는다.** 그래서 속도를 절반으로 낮춰 한 번 더 쟀다.

| # | 각변위 | 지령 | 예상 `d/v + v/a` | 실측 | 비율 | **초과** |
|---|---|---|---|---|---|---|
| 1 | 60.003° (J5) | 20°/s · 100°/s² | 3.20초 | 3.48초 | 1.087 | **0.28초** |
| 2 | 60.003° (J5) | 10°/s · 100°/s² | 6.10초 | 6.33초 | 1.037 | **0.23초** |

**가르는 것은 비율이 아니라 초과분이다.** velocity 가 배율 계열이면 초과분이 주행항(`d/v`)에 비례해
20°/s 쪽이 10°/s 쪽의 **절반**으로 나와야 한다. 실제로는 0.28 / 0.23 으로 거의 평평하다 —
속도와 무관한 **고정 오버헤드**의 서명이다. `t = d/(k·v) + v/a + c` 로 두 식을 풀면:

```
3.48 = 3.0/k + 0.2 + c
6.33 = 6.0/k + 0.1 + c      →   k = 1.017,   c = 0.330초    ← 🔴 이 두 값은 2단계에서 폐기됨
```

단위 문제는 여기서 닫혔다 — 경쟁 가설이 자릿수로 배제되기 때문이다. rad/s 면 20 rad/s = 1146°/s 라
0.05초, 정격 대비 %(180°/s) 면 36°/s 라 1.9초여야 했다. 실측 3.48초는 도/s 말고는 설명이 안 된다.

⚠️ **전제**: `get/velocity` 로 전역 배율이 **1** 인 것을 먼저 확인하고 쟀다. 08-05 세션이 0.51 을
남겨 두었다면 실측이 2배로 나와 단위를 오독했을 자리다. 재현할 때 이것부터 본다.

#### 2단계 — 🔴 k = 1.017 은 허상이었다 (16점 재측정)

같은 날 오후, Mark 가 *"관절 6개나 되니까 더 돌려봐"* 라고 해서 거리·속도·가속도를 **각각 독립적으로**
흔들어 14회를 더 쟀다 (J6 주축 + 다축 2회, 총 16점). 그 결과 **위의 `k = 1.017` 이 실재하지 않는
값**이라는 것이 드러났다.

**왜 허상이었나.** 1단계의 두 식은 `t = d/(k·v) + **v/a** + c` 라는 *사다리꼴 가정*을 강제한 채 풀렸다.
그런데 램프가 실제로는 사다리꼴보다 오래 걸린다. 모형이 그 부족분을 흡수할 칸이 `k` 밖에 없으니
최소자승이 그것을 **주행항으로 떠넘겼고**, 표본이 둘뿐이라 잔차가 0 이 되어 그 왜곡이 안 보였다.
표본 2개로 미지수 2개를 풀면 언제나 정확히 맞는다 — **맞는 것이 검증이 아니다.**

**이번엔 자유도를 확보했다.** 세 레버를 따로 흔들면 각 항이 독립적으로 관측된다:

| 흔든 것 | 관측 | 결론 |
|---|---|---|
| 속도 10~90°/s (거리 고정) | 초과분이 **속도에 비례** | 램프 항이 사다리꼴보다 크다 |
| 거리 60~270° (속도 고정) | 초과분이 **거리와 무관** | 주행항은 `d/v` 그대로 — 배율 계열 최종 배제 |
| 가속도 25~400°/s² (둘 고정) | 6.86 → 3.38초로 단조 감소 | `acceleration` 은 **실제로 먹는다** |

전 16점 최소자승 (`t = K·d/v + B·v/a + c`, 자유도 13):

```
K = 1.0002      ← 지령 속도는 오차 0.02% 로 그대로 지켜진다. k=1.017 은 없다
B = 1.5248      ← 램프에 v/a 의 1.525배가 걸린다
c = 0.1888초    ← 발행~플레이 왕복 + 정지 판정
```

| 모형 | RMS 잔차 | 최대 잔차 |
|---|---|---|
| 순수 사다리꼴 `d/v + v/a` | 0.289초 | 0.975초 |
| **`d/v + 1.525·v/a`** ← 채택 | **0.031초** | **0.049초** |
| `d/v + (π/2)·v/a` | 0.040초 | 0.079초 |

**B = 1.525 의 뜻**: 지령 가속도의 **실효값이 0.656·a** 다. `--accel 100` 은 실제로 66°/s² 처럼 거동한다.
저크가 다듬어진 프로파일이라는 뜻인데, π/2 = 1.5708 이 3% 옆에 있어 **코사인형 램프**를 시사한다.
다만 자유적합(1.525)이 π/2 고정보다 잔차가 낮아 정확히 π/2 라고 단정하지는 않는다.
저크 제한항(`a/j`)을 따로 넣어봤으나 계수가 사실상 0(−0.00006)으로 나와 **불필요**하다.

> 🔴 **이 문단의 코사인 램프 시사는 4단계에서 닫혔다.** 16점의 `v/a` 폭이 좁아 `B` 의 표준오차가
> 컸을 뿐이다. `a` 만 25~400 으로 흔들어 `v/a` 를 16배 벌리고 182점을 통합하니
> **B = 1.5392 ± 0.0053** — π/2 는 **6.0σ 로 배제**된다. 실효 가속도도 0.656 이 아니라 **0.65·a** 다.
> (통계오차 기준이고, 축별·설계별 계통오차는 안 갈랐다.)

**표본 밖 예측으로 검증했다** — 모형을 확정한 뒤 새 조건 둘을 *먼저 예측하고* 쟀다:

| 조건 | 예측 | 실측 | 오차 | 사다리꼴이었다면 |
|---|---|---|---|---|
| 270° · 75°/s · 150°/s² | 4.55초 | **4.59초** | 0.04 | 4.28초 (−0.31) |
| 120° · 25°/s · 60°/s² | 5.62초 | **5.59초** | 0.03 | 5.40초 (−0.19) |

**부수로 확인된 것 — 다축은 선행축이 지배한다.** 코드는 *"최대 각변위 축이 소요시간을 정한다"* 고
가정하는데(§2.4 게이트 ①) 그때까지 한 축만 돌려봐서 확인된 적이 없었다. 두 축을 동시에 돌려 갈랐다:

| 조건 | 선행축 지배 | 벡터 노름 지배 | 실측 |
|---|---|---|---|
| J5 90° + J6 90° | **3.64초** | 4.89초 | **3.68초** |
| J5 90° + J6 120° | **4.64초** | 5.64초 | **4.66초** |

선행축 지배가 맞다. 6축을 동시에 돌려도 시간은 최대 각변위 축 하나로 결정된다.

**축이 달라도 같다.** J5(손목 굽힘, 중력 부하 큼)와 J6(툴축 회전, 무부하)이 같은 모형을 따른다 —
1단계 J5 2점이 2단계 J6 12점과 함께 잔차 0.05초 안에 들어간다. 축별 보정은 필요 없다.

⚠️ **게이트 ③ 은 보수적이다.** 실측 램프각은 `½·B·v²/a = 0.77·v²/a` 인데 게이트는 `1.0·v²/a` 로 본다 —
실제로 가능한 이동을 30% 만큼 과하게 거부한다. **안전한 쪽으로 틀린 것이라 그대로 두었고**, 코드
주석과 실행 출력에 실측 기준값을 병기했다. 기본 30°/s 의 "9° 필요" 는 실제로는 6.9° 다.

**남긴 것**: 대조 출력은 지우지 않고 *회귀 감시*로 바꿨다. `expect_sec` 이 이제 실측 모형이므로
**비율이 1.00 근처**여야 정상이고, 벗어나면 전역 배율(`get/velocity`)부터 의심한다.

#### 3단계 — 6축 전수 확인, 그리고 `c` 가 상수가 아니라는 것

2단계까지는 **J5·J6 두 축**으로만 쟀다. Mark 지시 *"관절이 6개야. 다 하나하나 돌려보면서 수치 정확하게
해석해"* 로 나머지 넷을 포함해 **58회를 더** 돌렸다 (오늘 누적 **74회, 전부 도착오차 0.0000°**).

**먼저 축마다 안전 방향을 FK 로 정했다.** 단일축 이동은 관절공간에서 원호를 그리므로 끝점 두 개만
봐서는 중간에 바닥을 스치는지 알 수 없다. 그래서 경로를 13점씩 샘플링했다(`sweep.py`).

##### 🔴 `c` 는 상수가 아니다 — 이것이 이번의 진짜 발견 → **4단계에서 기각됨**

  (← 밴드 유지 결론도 살아남았다. 근거는 산포다.)

  사이에 낀다. 부하 효과라면 J6 이 가장 작아야 한다. **축 차이는 미확정으로 남긴다** (업무목록 L26).

#### 4단계 — 드리프트를 정면으로 재보고 **기각했다** (110점 추가)

3단계는 `c` 를 **묶음별로 나눠 평균**한 뒤 그 평균 넷이 커지는 것을 보고 드리프트라고 불렀다.
그런데 묶음은 시간뿐 아니라 **축·거리·속도·가속도가 통째로 다른** 덩어리다 — 시간이 원인이라는
근거가 설계 안에 없었다. 그래서 **시간 하나만 흔드는 실험**을 따로 짰다.

**4-1. 시간축 80점** — J6 에 **완전히 같은 지령**(v=60°/s, a=200°/s²)만 29분에 걸쳐 반복했다.
d=30° 짝(A)과 d=180° 짝(B)을 섞고, 중간에 **12.7분을 서보 ON 채로 놀렸다**.

| 왜 이 설계인가 | |
|---|---|
| 같은 지령만 반복 | 시간 외의 모든 변수가 상수다. 3단계가 못 가른 자리 |
| A(d=30) · B(d=180) 짝 | 램프 항은 공통, 주행 항만 6배. **고정 오버헤드가 끌리면 둘이 같은 초만큼**, **시간 배율이면 B 가 3.1배** 움직인다 |

**→ 드리프트는 없다.** 크기도 방향도 계통적이지 않고, 공백을 건너도 계단이 안 생긴다.

**4-2. 가속도 스윕 30점** — 같은 회차에 `a` 만 25~400 으로 흔들어(`v/a` 가 0.15~2.4, **16배 지렛대**)

**182점 통합 적합** (오전 2점을 뺀 전 회차 — `runs 14 · axes 24 · round2 16 · round3 18 · drift 80 · asweep 30`):


**무엇이 틀렸던 건가.** 회차 하나하나의 산포가 **0.035초**인데 묶음 크기가 n=14~24 였다.
묶음평균의 표준오차가 0.007~0.011초이니, 평균 넷이 0.19~0.23 사이에 흩어지는 것은 **잡음의 폭 그대로**다.
거기서 단조 증가를 읽은 것이 오독이었다. **평균 네 개는 추세를 판정할 표본이 아니다.**

**`c` 를 버스에서 분해했다.** MQTT `#` 를 통째로 관측해 `program/play` 발행부터 `program/end` 까지를 쪼갰다:

```
play 발행 ─18~22ms─ ack ─40~50ms─ RUN ─210~230ms─ 운동 시작 … 운동 끝 ─100~110ms─ program/end
```

- `program/play` 의 ack 는 **20ms** 다. 도착이 아니라 **접수**가 맞다 (앞선 "1.2초" 추정은 실행기가
  ack 와 도착을 인접한 줄에 찍어 외부 타임스탬프로는 못 가르던 탓의 허상이었다).
- 관측된 관절 운동 시간이 모형의 주행+램프 항보다 **정확히 0.122초 짧다** — d=30 에서 0.1225,
  d=180 에서 0.1215 로 **6배 거리 차이에도 셋째 자리까지 같다.** 거리 비례가 아니므로 물리가 아니라
  **판정 아티팩트**다: 정지 판정 임계 0.02° 가 램프의 완만한 시작·끝을 잘라먹는다.
  이 몫을 되돌려 놓으면 `c = 0.200` 이 정확히 재구성된다.

**남긴 것**: 대조 출력은 지우지 않고 *회귀 감시*로 바꿨다. `expect_sec` 이 이제 실측 모형이므로
**비율이 1.00 근처**여야 정상이고, 벗어나면 전역 배율(`get/velocity`)부터 의심한다.

**원자료**: 182점 CSV 6벌은 이 세션 스크래치에만 있다 — 리포에 남기지 않았다.
재현하려면 `--speed`/`--accel`/`--max-delta` 를 위 범위로 흔들어 실행기가 찍는 "실측" 값을 모으면 된다.
경로 안전 확인용 `sweep.py`(FK 13점 샘플링), 버스 관측기(`bus.py`)도 같은 자리에 있다.
⚠️ 버스 관측기를 다시 쓸 사람에게 — **CONNECT 의 keepalive 는 0 으로 둬라.** 60 으로 두고 PINGREQ 를
안 보내면 브로커가 **90초에 조용히 끊는다** (이 세션에서 1차 버스 로그를 그렇게 잃었다).

#### 부수 발견 — 서보 게이트가 없었다

이 측정의 첫 시도가 **서보 OFF** 상태에서 나갔다. `program/clear`·`plan`·`play` 세 ack 가 전부
`code:0` 으로 정상인데 로봇은 1mm 도 안 움직였고, 자세를 되읽으니 소수점 끝자리까지 발행 전과 같았다.
**ack 로는 이 상황을 알 수 없다** — 유일한 신호는 60초 타임아웃이었다.

`hcr5_comm/README.md` §6.1.3 이 *"서보 ON 필요"* 라고 적어 둔 조건인데 **실행기 어디에도 그것을 보는
코드가 없었다.** 게이트 ⓪~④ 는 전부 *내가 보낼 값*만 검사하고 *로봇이 받을 준비가 됐는지*는 아무도 안 봤다.
movel 도 같은 구멍이었다 — 서보가 켜진 세션에서만 돌려봐서 안 드러났을 뿐이다. → **게이트 ⑤** (§2.4).

### 2.4 안전 게이트 — 여섯 개, 전부 발행 전에

movel 의 게이트 셋에 **단위 표시**를 더한 넷으로 출발했다. movel 은 직교 좌표라 단위 혼동이 없었지만
movej 는 rad↔도 두 단위를 오가므로 그 칸이 필요하다(§2.2).
**⑤ 는 실측 중에 추가됐다** — §2.3 의 부수 발견.

| # | 게이트 | 기준 | 넘으면 |
|---|---|---|---|
| ⓪ | **단위** | rad · URDF도 · 실기도 **세 칸을 다 찍는다** | (표시 전용 — 사람이 본다) |
| ① | **각변위** | 최대 이동 축 \|Δ\| ≤ `--max-delta` (기본 **90°**) | 거부 |
| ② | **속도** | `--speed` ≤ `--max-speed` (기본 **50°/s**) | 거부 |
| ③ | **속도 프로파일 실현가능성** | 가감속 여유 `v²/a` ≤ 각변위 (실측 램프각 `0.77·v²/a` 보다 **보수적**) | 거부 |
| ④ | **관절 한계** | `withinLimits()` — ±360°, J3 ±165° | 거부 |
| ⑤ | **서보 상태** | `status/operation` = `SERVO_ON` | 거부 (`--plan-only` 는 면제) |

**⓪~④ 는 *내가 보낼 값*을 보고, ⑤ 는 *로봇이 받을 준비*를 본다.** 이 구분이 ⑤ 를 놓쳤던 이유다 —
게이트를 "내 실수를 막는 장치"로만 설계하면 로봇 쪽 전제조건은 아무도 안 본다.

게이트 ③ 은 movel 에서 그대로 가져왔다. **2026-08-05 의 150033 "특이점" 은 오진이었고 실제 원인은
가감속 거리 부족**이었다 (`hcr5_comm/README.md` §8 함정 1). 자세를 의심하기 전에 여기를 먼저 계산한다.
관절공간에서도 같은 조건이 성립하는지는 **미실측**이지만, 계산이 공짜이므로 걸어 둔다.

⚠️ **③ 의 기준식은 실측보다 30% 빡빡하다.** §2.3 에서 실제 램프각이 `0.77·v²/a` 로 나왔는데
게이트는 `1.0·v²/a` 를 쓴다 — 통과할 수 있는 이동 일부를 거부한다는 뜻이다. **안전한 쪽으로 틀렸으므로
식은 그대로 두고**, 실행 출력에 실측 기준값을 괄호로 병기했다. 거부가 억울하면 `--force` 로 넘긴다.

게이트 ① 은 새로 생긴 칸이다. 종전 movej 에는 없었다 —
movel.md §2.4 의 *"`10` 을 `100` 으로 오타 내면 그대로 10배를 간다"* 와 같은 구멍이 관절공간에도 있다.
`--speed` 가 각속도만 보므로 **총 이동량은 아무도 안 본다.**

기본 눈금은 **`--speed` 30°/s · `--max-speed` 50°/s** 다 (Mark, 2026-08-16 — *"기본 50. `--speed`는 기본 30.
너무 느려"*). 착수 시점에는 종전 movej 의 2 / 10 을 그대로 이어받았는데, 그것은 §2.3 의 단위가
미확정인 동안의 보수값이었다. 도/s 가 확정되고 실기 2회가 무사히 끝나면서 유지할 이유가 없어졌다.
상한 50 은 펜던트 캡처의 joint 기본값과 같은 자리다.

> "지금 현재까지 로봇을 여러번 돌려보았지만 움직임은 속도가 매우 느리고, 관절한계도 크게 문제가 없었어."
> (movel.md §2.4, Mark)

⚠️ **의미가 달라졌다.** 종전 `--speed` 는 PC 가 궤적 duration 을 계산하는 데만 쓰였고 실기에
전달되지 않았다. 이제는 **컨트롤러에 그대로 실린다.**

⚠️ **게이트 ③ 과의 상호작용** — 기본 속도가 30°/s 로 오르면서 게이트가 `v²/a` = **9°** 를 요구하게 됐다
(실제 램프각은 6.9° 다 — 위의 보수성 주석 참조).
그보다 짧은 이동은 게이트 ③ 이 거부한다(거부 메시지가 그 구간에서 낼 수 있는 최대 속도를 알려준다).
`--speed` 를 낮추거나, 짧은 이동을 자주 한다면 `--accel`(기본 100°/s²) 을 올리는 쪽이 맞다.
속도 기본값만 올리고 가속도를 그대로 둔 결과라 의도된 것이다 — 가속도 100 은 컨트롤러 기본값이다.

### 2.5 왜 `move/joint/here` 가 아닌가

`hcr5_comm/README.md` §4.1 은 `move/joint/here {jointAngle:[j1..j6]}` 를 **"절대 관절이동 ★"** 로 올려 두고,
§5.2 가 **이미 실증**했다고 적는다(도달오차 0.0000°, 61° 를 6.3초에 자율주행). §6 첫 문장도
*"단발 자세 이동은 `move/joint/here` 로 충분하다"* 고 한다. 코드도 훨씬 짧아진다 — FK 도 봉투도 필요 없다.

**그럼에도 `program/plan` 을 골랐다** (Mark 판단, 2026-08-16). 이유 셋:

| | `move/joint/here` | **`program/plan` joint** |
|---|---|---|
| 속도 지정 | ❌ **명령에 못 싣는다.** 전역 `set/velocity`(0~1 배율)로만 조절되고 기준 속도가 미상 | ✅ 노드마다 `velocity`·`acceleration` |
| 두산 `MoveJoint` 대응 | 부분 (pos 만) | ✅ pos·vel·acc 가 그대로 대응 (§3.2) |
| movel 과의 대칭 | 다른 경로 — 코드도 문서도 두 벌 | ✅ **같은 문, `selected` 만 다르다** |

첫 칸이 결정적이다. **movej 의 존재 이유가 속도 게이트**인데(`move_common.hpp:3-11` — *"이 경로에 속도
안전망이 하나도 없다… 계산이 곧 안전장치였다"*), 명령에 속도를 못 싣는 경로로 내려가면 그 게이트가
계산만 하고 아무것도 못 막는 **장식**이 된다. 전역 배율을 건드리는 것은 다른 세션·다른 도구의 속도까지
바꾸는 일이라 더 나쁘다.

> `move/joint/here` 를 버리는 것은 아니다. **`servo` 와 같은 급의 비상·단발 수단**으로 남는다
> (`mqtt_cmd.py movej` 가 이미 그 자리에 있다 — README:640).

## 3. 두산 로봇암 조사결과

**질문** — 두산의 `movej` 는 `movel` 과 같은 층인가, 아니면 관절 이동만 다른 문으로 빠지는가?
**답 — 같은 층이다. `MoveJoint` 도 컨트롤러가 보간을 소유한다.** 그리고 **딱 한 필드가 빠져 있는데
그 빠짐이 의미가 있다.**

### 3.1 확인된 사실

두산 ROS 2 패키지 `doosan-robot2` 의 `movej` 는 **`motion/move_joint` 서비스**(`dsr_msgs2/srv/MoveJoint`)를
호출한다. 요청 필드:

```
pos[6], vel, acc, time, radius, mode, blendType, syncType
```

`movel`(`MoveLine`) 과 나란히 놓으면:

```
movel :  pos, vel, acc, time, radius, ref, mode, blend_type, sync_type
movej :  pos, vel, acc, time, radius,      mode, blend_type, sync_type
                                     ↑
                              ref 가 없다
```

**`ref`(reference frame) 가 `movej` 에만 없다.** 파이썬 래퍼도 같다 —
`movel(pos, vel, acc, time, radius, ref, mod, ra, …)` vs `movej(pos, vel, acc, time, radius, mod, ra, …)`.
두산 매뉴얼도 *"movej 는 각 관절 각도를 지정하며 **기준 좌표를 설정하지 않는다**"* 고 적는다.

→ **관절공간에는 기준 원점이 없다.** movel.md §2.2 가 `<좌표계>` 토큰에 한 절을 쓴 그 축이
`movej` 에는 **아예 존재하지 않는다.** 우리 구현에 좌표계 인자를 넣지 않은 것이 이 근거다(§1.1 표).

**단위** — 두산 프로그래밍 매뉴얼:

| 파라미터 | 단위 |
|---|---|
| `vel` | **deg/sec** |
| `acc` | **deg/sec²** |
| `radius` | mm (블렌딩 반경) |
| `time` | sec — ⚠️ **주면 vel·acc 를 무시한다** |
| `mode` | `DR_MV_MOD_ABS`(절대) / `DR_MV_MOD_REL`(상대) |

`vel`·`acc` 가 **도 계열**인 것이 §2.3 가설의 근거 하나다.

### 3.2 우리 HCR-5 의 대응물

**`program/plan` 의 `move.selected:"joint"` 가 같은 자리다.**

| 두산 `MoveJoint` | HCR-5 `program/plan` joint | 비고 |
|---|---|---|
| `pos[6]` | `waypoint.endPoint.fixed.joint` | HCR-5 는 tcp·flange 도 **함께** 담는다 → FK 필요 (§1.2) |
| `vel` (deg/s) | `move.joint.velocity` | ✅ **도/s 로 실측 확정** — §2.3. 펜던트 기본 50 |
| `acc` (deg/s²) | `move.joint.acceleration` | 〃 기본 100 |
| `radius` | **없다** | ⚠️ **차이.** radius 는 `linear` 에만 있다 (§1.2) |
| `mode` (abs/rel) | 대응 미확인 | 우리는 절대만 구현 — §4 후속 |
| `blend_type` | `move.joint.continues` | linear 와 같은 키 |
| `sync_type` | `program/play` 후 `program/end` 대기 | ack ≠ 도착 |
| `time` | 대응 없음 | 두산은 시간 지정 시 vel·acc 를 무시한다 |
| ~~`ref`~~ | ~~—~~ | **양쪽 다 없다** — §3.1 |

두 표(이것과 movel.md §3.2)를 겹쳐 보면 **`ref` 칸 하나만 빠지고 나머지가 그대로 겹친다.**
movel.md 가 *"우연이 아니라 산업로봇 모션 명령의 공통 형태"* 라고 한 관찰이 관절공간에서도 성립한다.

### 3.3 그래서 무엇이 바뀌었나

**`movel` 때만큼 극적이지 않다.** movel 은 이름과 동작이 어긋나 있었다(직선이라 이름 붙었는데 호를 그렸다).
`movej` 는 **JTC 경로에서도 이름대로 동작했다** — 관절공간 보간이니 관절 궤적이 맞았다.

바뀐 것은 **정확성이 아니라 자립성과 판정력**이다:

| | 종전 (JTC) | 교체 후 |
|---|---|---|
| 동작의 옳고 그름 | ✅ 맞았다 | ✅ 맞다 |
| 스택 없이 도는가 | ❌ `bringup.launch.py` 필요 | ✅ 단독 |
| 도착을 프로그램이 판정하는가 | ❌ 사람이 `mqtt_cmd.py pos` 로 | ✅ `program/end` + 자세 되읽기 |
| movel 과 같은 문인가 | ❌ 두 벌 | ✅ 한 벌 |

세 번째 칸이 이 세션의 실제 목적이다 — §2.1 ③.

검토한 대안 둘 중 `program/plan` joint 를 골랐다:

| | 방식 | 속도 지정 | 판단 |
|---|---|---|---|
| A | `move/joint/here` | ❌ 전역 배율만 | 실증은 있으나 속도 게이트가 무력해진다 (§2.5) |
| **B** | **`program/plan` joint** | ✅ 노드별 vel·acc | ✅ **채택** — 두산과 같은 층, movel 과 같은 문 |
