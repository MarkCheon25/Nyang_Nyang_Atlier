## 1. 개요

### 한 줄

사용자가 올린 **실물 고양이 사진**을 OpenAI `gpt-image-2` 로 **캐리커쳐 PNG** 로 바꾼다.
그 PNG 를 dy 의 SAM3 노드가 그대로 받아 부위를 딴다.

### 파이프라인에서의 자리

```
실물 고양이 사진 (사용자 업로드)
   │
   ├─ ① llm        (이 모듈 · 신규)   gpt-image-2 /v1/images/edits
   ↓
캐리커쳐 PNG        ← cat_char.png 형식
   │
   ├─ ② sam3_extract_ros_node.py (dy · 무수정)   → /vision_parts  (MaskImage)
   ├─ ③ contour_pixel_node.cpp   (dy · 무수정)   → /vision/strokes (Stroke)
   ↓
   └─ ④ moveit2 (g0ranii)  →  HCR-5  →  A4
```

**동료 코드는 한 줄도 고치지 않는다.** ①의 출력이 ②의 입력 형식을 맞추는 쪽으로 설계했다.

### 왜 이 칸이 필요한가 — 실측 근거

dy 가 올린 산출물을 열어 확인했다 (2026-08-16, 커밋 `0c8dddd`):

| 확인한 것 | 값 |
|---|---|
| `sam3_output/metadata.json` 의 `image_path` | `/home/dorong/cat_char.png` |
| 이미지 크기 | 480 × 538 |
| `sam3_extract_ros_node.py:215` 의 입력 | `CURRENT_DIR / "cat_char.png"` 하드코딩 |
| `cat_char.png` 의 정체 | **두꺼운 균일 검은 외곽선 + 단색 채움**의 벡터풍 고양이 일러스트. 실물 사진이 아니다 |

즉 **dy 의 파이프라인은 이미 "캐리커쳐를 받아 부위를 딴다"로 만들어져 있다.**
비어 있는 것은 *그 캐리커쳐를 사용자 사진에서 만들어내는 칸* 하나다 — dy 는 그림을 손으로
구해다 놓았다. 이 모듈이 그 손을 대신한다.

> 이 사실이 설계를 크게 줄였다. SAM3 가 캐리커쳐 위에서 도는 이상 **좌표계가 하나뿐**이라,
> "사진 좌표의 마스크를 캐리커쳐에 얹는" 정합 문제가 아예 생기지 않는다.
> (검토 과정에서 그 병렬 구조를 후보로 놓았다가, 위 실측으로 폐기했다.)

### 목표 출력의 정의

"라인아트"라는 말은 너무 넓다. **`cat_char.png` 가 기준이다:**

- 두껍고 굵기가 일정한 검은 외곽선
- 단색(또는 매우 단순한) 채움 — 그라데이션·해칭·스티플링 없음
- 밝은 단색 배경
- 얼굴 · 몸 · 다리 · 꼬리 · 눈 · 코 · 입이 **닫힌 선으로 서로 구분**됨
- 원본 고양이의 자세·비율·특징을 알아볼 수 있을 것

마지막 두 줄이 이 모듈의 진짜 제약이다. **예쁜 그림이 아니라 SAM3 가 부위를 나눌 수 있는
그림**이어야 한다.

### 성공 판정

**사람이 눈으로 판정한다** (Rokey6 결정 2026-08-16). 자동 지표를 게이트로 쓰지 않는다.

다만 눈 판정을 돕는 참고 수치가 하나 있다 — 같은 사진을 프롬프트 3종으로 돌린 뒤
②를 태워 **SAM3 confidence** 를 비교한다. `cat_char.png` 의 실측값이 대조군이 된다:

| 부위 | cat_char.png 기준값 |
|---|---|
| cat | 0.9723 |
| eye of cat (좌 / 우) | 0.9077 / 0.9138 |
| nose of cat | 0.8621 |
| mouth of cat | 0.8323 |

> ⚠️ **이 수치는 통과 기준이 아니라 대조군이다.** 낮아도 그림이 좋으면 채택할 수 있고,
> 높아도 그림이 못 쓸 것이면 버린다. 판정 주체는 사람이다.

### 확정 사실 — OpenAI 이미지 API

developers.openai.com 에서 **2026-08-16 직접 확인**했다. 기억이나 예제를 믿지 말 것.

| 항목 | 값 |
|---|---|
| 모델 | `gpt-image-2` (기본 스냅샷 `gpt-image-2-2026-04-21`, 2026-04-21 출시) |
| 엔드포인트 | **POST** `https://api.openai.com/v1/images/edits` |
| 형식 | `multipart/form-data` |
| 필수 | `model` · `image` · `prompt` |
| 선택 | `mask` · `size` · `quality` · `background` · `output_format` · `output_compression` · `n` |
| 마스크 | **선택이다.** 전체를 다시 그리므로 우리는 보내지 않는다 |
| 이미지 여러 장 | `image[]` 로 **최대 16장**까지 보낼 수 있다. 마스크를 보내면 첫 장에만 걸린다 (2026-08-16 확인) |
| 입력 이미지 | PNG / JPEG / WebP, **50MB 미만** |
| `size` 제약 | `auto` 또는 `<W>x<H>` — 양변이 **16의 배수**, 최대변 ≤ 3840, 종횡비 ≤ 3:1, 총 픽셀 655,360 ~ 8,294,400 |
| `quality` | `low` · `medium` · `high` · `auto` |
| 응답 | **base64** (`b64_json`), 기본 PNG |
| 과금 | 장당 정가 없음 — **토큰 과금**. 이미지 출력 $30/1M · 이미지 입력 $8/1M · 캐시 입력 $2/1M · 텍스트 입력 $5/1M. Batch 는 전부 50% |
| 장당 추정 | 1024×1024 기준 low **$0.006** · medium **$0.053** · high **$0.211** |
| **입력 토큰 계산** | 이미지의 **가로×세로**로 정해진다. 격자로 잘라 조각 수를 세는 방식이다 |
| ⚠️ 전제 | **조직 인증(API Organization Verification)이 필요할 수 있다** |

> `input_fidelity` 는 gpt-image-2 에 **해당 없음**으로 문서에 명시돼 있다. 구도 보존을 이
> 파라미터로 제어할 수 없다.

> ⚠️ **흑백으로 바꿔도 토큰은 줄지 않는다.** 입력 토큰은 가로세로로만 정해지므로 색이 몇
> 개든 조각 수가 같다. 흑백 변환은 **파일 용량**을 줄일 뿐이다.
> 입력 토큰을 줄이는 유일한 손잡이는 **크기 축소**다.
>
> 여기에 비대칭이 하나 있다 — 16의 배수·총픽셀 655,360 이상 같은 크기 규칙은 **출력에만**
> 걸린다. **우리가 보내는 사진은 얼마든지 작게 줄일 수 있다.**

> ⬜ **`gpt-image-2` 존재 여부를 미확인으로 되돌린다** (2026-08-16 재확인 시도).
> 위 표는 08-16 에 developers.openai.com 에서 읽은 값인데, 같은 날 재검색에서는
> `gpt-image-1.5` · `gpt-image-1` · `gpt-image-1-mini` 만 나오고 `gpt-image-2` 가
> 보이지 않았다. **키가 생긴 뒤 실호출로 확정한다.** 모델 이름 외의 나머지 값
> (엔드포인트·형식·크기 규칙·과금 구조)은 계열 공통이라 그대로 쓴다.

### 보류한 것 — 비교 검증

동료의 SAM3 경로가 정말 필요한지 확인하는 별도 패키지(`vision_probe`)를 설계했다가
**이번 범위에서 뺐다.** 나중에 다시 꺼낼 수 있게 근거만 남긴다.

- **질문** — 입력이 이미 평평한 2색 그림인데 SAM3 같은 AI 분할 모델이 필요한가.
  SAM3 뒤에서 `contour_pixel_node.cpp` 가 어차피 `findContours` 로 다시 테두리를 뽑는다.
  평평한 2색 그림에서 영역을 나누는 것은 연결 영역 라벨링으로 충분할 수 있다
- **SAM3 가 주는 것** — 부위 이름("이건 눈이다")과, 입력이 지저분해도 버티는 강인함.
  뒤쪽 걱정은 위에서 정한 **이진화 후처리**가 상당히 덜어 준다
- **성사되면 얻는 것** — 파이썬·가상환경·SAM3 가중치가 통째로 빠지고 파이프라인
  전체가 C++ 컨테이너 하나가 된다. 프로젝트 규칙 N1(전 구간 C++)과도 맞는다
- **비교에 필요한 재료는 이미 리포에 다 있다** — dy 가 입력 그림
  (`vision_node/src/cat_char.png`, `cat_char2/3.png`)과 SAM3 결과 마스크 5장,
  신뢰도가 적힌 `sam3_output/metadata.json` 을 커밋해 두었다.
  **API 호출도 로봇도 없이 오프라인으로 전부 비교된다**
- **하게 되면 이름은 붙이지 않는다** — 확인하려는 것은 *영역이 같은가*이지
  *이름을 맞힐 수 있는가*가 아니다. 위치 휴리스틱은 `cat_char.png` 한 장에만 맞을
  위험이 크고 비교 결과에 자기 오차를 섞는다. 겹친 넓이가 가장 큰 것끼리 짝지으면 된다
- **숫자가 나오기 전에는 동료에게 제안하지 않는다**

### 미결

- **구도 보존 여부 미실측** — `/v1/images/edits` 가 입력 사진의 구도를 어느 정도 지키는지
  확인하지 않았다. 지금 설계는 이것에 **의존하지 않지만**, 보존이 잘 되면 원본 사진과
  나란히 놓고 비교하기 쉬워진다
- **프롬프트 미확정** — 3종 프리셋을 만들어 두었으나 어느 것도 실사진으로 검증하지 않았다
- **`size` 선택 미확정** — 정사각형이 가장 빠르다고 문서가 말하지만, A4 세로에 그리므로
  세로가 긴 쪽이 여백을 덜 남긴다. 실측 후 정한다
- **API 키·크레딧·조직 인증 미확보** — 아래 §3 참조
- **모델 이름 미확정** — `gpt-image-2` 가 실재하는지. 위 '확정 사실' 의 ⬜ 참조
- **입력 토큰 계수 미확인** — 가로세로에서 토큰이 나오는 방식은 계열 공통이지만,
  정확한 계수는 실호출로 확인한다. `--max-edge` 기본값(1024)은 그 전까지 잠정값이다
- **재현성 수단 미확인** — 같은 프롬프트로 두 번 돌리면 다른 그림이 나온다.
  이미지 API 에 난수 씨앗(seed) 옵션이 있는지 확인하지 않았다. 있으면 프롬프트
  비교가 훨씬 깨끗해지므로 키 확보 시 함께 확인한다
- **이진화 임계값 미확정** — 자동(Otsu)으로 시작한다. 생성 그림의 배경까지 회색이면
  자동이 엉뚱한 곳을 자를 수 있다. 실측 후 고정값으로 바꿀지 정한다

## 2. 구성

> ⬜ **아직 코드가 없다.** 이 절은 세션 `260816-랙기어` 에서 정한 뼈대이고,
> 구현하면서 어긋나는 곳은 이 문서를 고친다.

### 파일 배치

```
src/vision/ws_vision/src/vision_stylize/
├── include/vision_stylize/
│   ├── types.hpp           데이터 구조 · 오류 구분
│   ├── image_io.hpp        이미지 파일 읽기 · 쓰기 · 형식 판별
│   ├── image_ops.hpp       전처리(축소·흑백·여백) · 후처리(이진화)
│   ├── prompt_preset.hpp   프롬프트 파일 불러오기
│   ├── api_client.hpp      OpenAI 통신
│   └── cost_guard.hpp      예상 비용 · 중복 호출 방지
├── src/
│   ├── (위 각각의 .cpp)
│   └── stylize_cli.cpp     명령줄 프로그램
├── prompts/
│   └── conservative.txt · balanced.txt · minimal.txt
├── CMakeLists.txt
└── package.xml
```

**ROS 없이도 빌드되고 실행된다.** 순수 C++ 라이브러리 위에 명령줄 프로그램을 하나
얹는다 — `vision_core` 가 이미 쓰는 2층 방식이다. `rclcpp` 는 어디에도 없다.

의존은 **libcurl · nlohmann/json · OpenCV** 셋이다. OpenCV 는 전처리·후처리에서만
쓰고, 컨테이너에 이미 들어 있다.

### 파일마다 무슨 일을 하는가

**`types.hpp` — 데이터 구조와 오류 구분**

프로그램 안에서 오가는 값들의 모양만 적는다. 이미지 한 장(바이트 + 형식 + 파일명),
요청 한 건(사진 + 참조 그림 + 프롬프트 + 설정), 결과 한 건(PNG + 해시 + 비용).
여기가 얇아야 나머지 파일들이 서로를 모른 채 있을 수 있다.

실패도 여기서 두 갈래로 나눈다.

| 갈래 | 언제 |
|---|---|
| 보내기 **전** 실패 | 파일 없음 · 형식 아님 · 크기 규칙 위반 |
| 보낸 **뒤** 실패 | 서버가 거절 · 전송 오류 |

뒤쪽은 다시 **다시 보내면 될 것**(429 · 5xx · 전송 오류)과 **다시 보내봐야 같은
실패에 돈만 나가는 것**(그 밖의 4xx)으로 갈린다. **이 판정을 하는 함수를 하나만
둔다.** 여러 곳에서 상태 코드를 보고 나누기 시작하면 규칙이 흩어지고 그중 하나만
고쳐지는 사고가 난다.

**`image_io.hpp` — 이미지 파일 읽기·쓰기**

파일을 바이트로 읽고, 정말 PNG/JPEG/WebP 인지 확인하고, 50MB 를 넘지 않는지 본다.
확장자를 믿지 않고 파일 앞머리 몇 바이트를 직접 본다. 저장할 때도 받은 바이트를
그대로 쓴다 — **여기서는 이미지를 픽셀로 풀지 않는다.**

**`image_ops.hpp` — 전처리와 후처리**

픽셀을 만지는 일은 전부 이 파일에 모은다.

*전처리(보내기 전)* — 사진 가장자리의 균일한 여백을 잘라내고, 색을 지우고, 긴 변을
정해진 크기로 줄인다. 종횡비는 유지하고 남는 곳은 흰 여백으로 채운다(고양이가
잘리지 않게). 무슨 일이 있었는지는 기록으로 남겨 요약 파일에 들어간다.

- **크기 축소가 입력 토큰을 줄이는 유일한 손잡이다.** 흑백 변환은 토큰과 무관하다
- **여백 잘라내기가 은근히 크다.** 고양이가 차지하는 비율이 올라가 같은 토큰으로 더
  많은 정보를 보낸다
- **전처리한 사진을 파일로 남긴다.** 결과가 이상할 때 "무엇을 보냈길래" 를 되짚을
  유일한 방법이다

*후처리(받은 뒤)* — 받은 PNG 를 이진화해 순수 2색으로 만든다. **원본은 그대로 두고
이진화본을 따로 저장한다.** 다음 단계에 넣는 것은 이진화본이다.

이 후처리가 있는 이유는 **부탁해서 되는 것과 강제할 수 있는 것을 나누기 위해서다.**
안티앨리어싱된 회색을 잘라내는 일은 우리가 하면 확정이고, 모델에게 부탁하면 될 때도
있고 안 될 때도 있다. `llm_script.md` §L2 가 지목한 함정 중 첫 번째(육안으로는 선
그림인데 실제로는 안티앨리어싱된 회색 그라데이션이라 이진화 임계값에 민감하다)가
이걸로 **프롬프트 문제에서 임계값 문제로 내려온다.**

**`prompt_preset.hpp` — 프롬프트 불러오기**

프롬프트를 소스에 문자열로 박지 않고 `prompts/` 안의 텍스트 파일로 두고 읽는다.
프롬프트는 실험으로만 정해지는데, 코드에 있으면 한 글자 고칠 때마다 다시 빌드해야
한다. 파일이면 빌드가 없고 git 에서 프롬프트 변화만 따로 읽힌다.

설치 경로를 찾는 일은 **명령줄 프로그램 쪽에서 한다.** 라이브러리는 경로를 받기만
한다 — 설치 경로 조회에는 `ament_index` 가 필요한데 그걸 라이브러리에 넣으면
"ROS 없이도 빌드된다" 가 깨진다.

**`api_client.hpp` — OpenAI 통신**

요청을 만들어 보내고 답을 받는다. 사진과 참조 그림을 multipart 로 싣고, 돌아온
base64 문자열을 이미지 바이트로 되돌린다. 재시도 판단은 스스로 하지 않고
`types.hpp` 의 규칙을 따른다.

- **`image[]` 에 대상 사진이 먼저, 참조 그림이 뒤.** 순서가 "무엇이 편집 대상인가" 를 뜻한다
- **API 키는 헤더로만 실린다.** 명령행 인자로 키를 받는 경로를 두지 않는다 —
  `ps` 와 셸 히스토리에 그대로 남는다
- **주소를 생성자에서 받는다.** 시험할 때 가짜 서버를 물릴 수 있어야 한다

**`cost_guard.hpp` — 예상 비용과 중복 호출 방지**

호출마다 돈이 나가므로 **보내기 전에** 얼마가 나갈지 계산해 보여주고 동의를 받는다.
그리고 사진·프롬프트·설정을 하나의 해시로 접어 결과 파일 이름에 넣는다. 같은
요청이면 이미 있는 파일을 쓰고 보내지 않는다. 덤으로 "이 PNG 가 어떤 프롬프트에서
나왔나" 를 파일 이름만 보고 알 수 있다.

- 해시 대상은 **전처리 후** 사진 바이트 · 참조 바이트 · 프롬프트 원문 ·
  모델 / 크기 / 품질 / 배경. 전처리 설정만 바꿔도 다른 요청이 된다
- 예상 비용 계산에 **참조 그림도 넣는다.** 한 장이 늘면 입력 토큰이 늘기 때문이다.
  이 값이 "참조를 함께 보내는 것이 값어치를 하는가" 를 숫자로 답한다

**`stylize_cli.cpp` — 명령줄 프로그램**

위 라이브러리들을 순서대로 엮어 실제로 돌린다. 성공 판정을 사람이 눈으로 하므로,
이 프로그램의 목적은 **프롬프트 3종 결과를 같은 사진으로 만들어 나란히 놓는 것**이다.
숫자는 화면에, 그림은 파일로 나간다.

### 실행 순서

```
 1. 인자 해석
 2. API 키 확인                       ← 없으면 여기서 끝. 돈 쓰기 전에 실패한다
 3. 사진 읽기 (+ 참조 그림)
 4. 전처리 → 보낼 바이트 확정 + 기록
 5. 전처리 결과를 파일로 저장
 6. 출력 크기 규칙 검사
 7. 쓸 프롬프트 목록 정하기
    ┌ 프롬프트마다 ─────────────────────────
 8. │ 프롬프트 읽기
 9. │ 요청 해시 계산 (전처리된 바이트 기준)
10. │ 이미 만든 결과가 있는지 확인      ← 있으면 이번 것은 건너뛴다
11. │ 예상 비용 더하기
    └───────────────────────────────────
12. 총액을 한 번에 보여주고 동의 받기   ← 미리보기 모드면 여기서 끝
    ┌ 프롬프트마다 ─────────────────────────
13. │ 요청 보내기
14. │ 받은 PNG 저장
15. │ 이진화본 저장
16. │ 조건 기록 남기기
    └───────────────────────────────────
17. 결과 표 출력
```

**검사와 비용 계산을 전부 앞에 몰아둔 것이 요점이다.** 프롬프트마다
"계산 → 동의 → 전송" 을 반복하면 사용자가 세 번 답해야 하고, 두 번째에서 실패하면
첫 번째 돈만 나간 어중간한 상태가 된다.

### 산출물

`data/out/` 아래에 떨어진다. 컨테이너 밖 호스트에서 바로 열린다.

| 파일 | 내용 |
|---|---|
| `input_<해시12>_sent.png` | 실제로 보낸 사진 (전처리 결과) |
| `<프리셋>_<품질>_<해시12>.png` | API 가 준 바이트 그대로 |
| `<프리셋>_<품질>_<해시12>_bw.png` | 이진화본. **다음 단계 입력** |
| `<프리셋>_<품질>_<해시12>.txt` | 프롬프트 원문 · 크기 · 품질 · 비용 · 전처리 기록 |

예 — `balanced_low_a3f19c2b74e1.png`

### 발산을 무엇으로 막나

같은 프롬프트로 두 번 돌려도 다른 그림이 나오고, 지시를 어기기도 한다. 막는 수단이
여럿인데 **세기가 크게 다르다.** 강한 순서로 적는다.

| 수단 | 어디서 | 왜 세거나 약한가 |
|---|---|---|
| ① 참조 그림 함께 보내기 | `api_client` | 스타일을 말로 열 줄 묘사하는 것보다 그림 한 장이 압도적이다 |
| ② 입력에서 색 지우기 | `image_ops` 전처리 | 지시를 어길 재료를 미리 없앤다. 부탁이 아니라 제거다 |
| ③ 받은 뒤 우리가 확정 | `image_ops` 후처리 | 2색으로 줄이는 일은 우리가 하면 확정이다 |
| ④ 프롬프트 | `prompts/*.txt` | 위 셋이 못 잡는 것(자세·구도·부위 분리)만 맡는다 |

**④ 를 쓸 때의 방침 — 금지보다 숫자.** "그라데이션 쓰지 마" 보다 "정확히 2색" 이
잘 듣는다. 부정문은 그 단어를 오히려 떠올리게 하고, 숫자는 어길 여지가 없다.

| 이렇게 쓴다 | 이렇게 쓰지 않는다 |
|---|---|
| 정확히 2색 — 검정 선, 흰 배경 | 그라데이션·해칭·스티플링 쓰지 마 |
| 외곽선 굵기는 이미지 높이의 약 2%, 전 구간 균일 | 선을 굵게 |
| 머리·귀·눈 2개·코·입·몸·다리·꼬리가 각각 **닫힌 선으로 분리** | 부위가 구분되게 |
| 입력 사진과 같은 자세·같은 화면 구성, 전신이 다 들어오게 | 원본을 살려서 |

세 번째 줄이 이 프롬프트의 진짜 목적이다. **예쁜 그림이 아니라 부위를 나눌 수 있는
그림**이어야 한다. 다음 단계가 찾을 부위 이름을 프롬프트에 그대로 적어, 앞 단계와
뒷 단계가 같은 단어를 쓰게 만든다.

## 3. 설치

> 이 절은 **아직 실행으로 검증되지 않았다.** 코드가 서면 실측값으로 갱신한다.

### (1) API 키

**키를 리포에 커밋하지 않는다.** 환경변수로만 다룬다. 파일로 두려면 **작업 트리 밖**에
두고 셸이 읽어 넘긴다:

```bash
# 최초 1회 — 리포 밖에 둔다
install -m 600 /dev/null ~/.openai_key
# (에디터로 키를 붙여넣는다. 이 명령을 셸 히스토리에 남기지 말 것)

# 사용할 때
export OPENAI_API_KEY="$(cat ~/.openai_key)"
```

- 명령행 인자로 키를 받는 경로는 **두지 않는다** — `ps` 와 셸 히스토리에 그대로 남는다
- 입력 사진과 생성 결과는 `src/vision/data/` 에 둔다 — 이미 `.gitignore` 에 있다
  (디렉터리는 아직 실재하지 않으니 만들어야 한다)

### (2) 조직 인증 · 크레딧

`platform.openai.com` 에서:
- API 키 발급
- **API Organization Verification** — gpt-image-2 계열은 이것이 필요할 수 있다
- 선불 크레딧 필요 여부 확인

> ⬜ **미확인.** 04pc 에 `OPENAI_API_KEY` 가 설정돼 있지 않고 python `openai` 패키지도 없다
> (2026-08-16 실측).

### (3) 빌드 의존

| 의존 | 왜 | 상태 |
|---|---|---|
| libcurl | HTTPS multipart 전송 | ⬜ vision `Dockerfile` 에 없음 — 추가 필요 |
| nlohmann/json | 응답 JSON 파싱 | ⬜ 없음 — 추가 필요 |
| OpenCV | 전처리(축소·흑백·여백) · 후처리(이진화) | ✅ 이미 들어 있다 (contrib 포함) |

앞의 둘은 apt 로 들어오지만 **이미지 재빌드(5~15분)가 따른다.**

base64 디코드는 직접 구현한다(약 30줄). 이것 하나 때문에 의존을 더 늘리지 않는다.

```bash
cd src/vision
./run_container.sh build
./run_container.sh shell
colcon build --symlink-install
source install/setup.bash
```

## 4. 실행

> ⬜ **아직 동작하지 않는다.** 아래는 예정 형태다. 코드가 서고 실제로 한 번 돌린 뒤에
> 실측 절차로 갱신한다.

```bash
export OPENAI_API_KEY="$(cat ~/.openai_key)"

# 프롬프트 3종을 같은 사진에 돌려 나란히 본다
ros2 run vision_stylize stylize_cli \
    --in  ~/data/my_cat.jpg \
    --ref ~/data/cat_char.png \
    --out-dir ~/data/out \
    --preset all \
    --quality low
```

### 명령줄 옵션

```
stylize_cli --in <사진> --out-dir <경로>
            [--ref <참조PNG>]                  없으면 프롬프트만으로 진행
            --preset <이름|all>
            [--quality low|medium|high|auto]   기본 low
            [--size auto|WxH]
            [--model <스냅샷이름>]
            [--max-edge <픽셀>]                기본 1024. 입력 토큰의 손잡이
            [--no-grayscale] [--no-trim]
            [--fit contain|cover|stretch]      기본 contain
            [--no-binarize]
            [--prompt-dir <경로>]
            [--dry-run]                        비용만 보고 끝낸다
            [--yes]                            동의를 묻지 않는다
            [--no-cache]                       기존 결과를 무시하고 다시 보낸다
```

- **API 키는 환경변수 `OPENAI_API_KEY` 에서만 읽는다.** 인자로 받는 경로를 두지 않는다
- 프롬프트 디렉터리는 `--prompt-dir` → 환경변수 `STYLIZE_PROMPT_DIR` →
  실행파일 상대 경로 순으로 찾는다
- **품질 기본값이 `low` 인 이유** — 프롬프트를 정하는 동안 회차가 가장 많이 돈다.
  확정한 뒤에 올린다 (low $0.006 → high $0.211, 약 35배)

이어서 dy 파이프라인에 태운다 (dy `README.md` §실행 방법 참조):

```bash
# 비전 컨테이너
ros2 run vision_node contour_pixel
# 가상환경에서
python3 sam3_extract_ros_node.py     # ← 입력 경로가 하드코딩이라 지금은 파일을 바꿔 넣어야 한다
```
