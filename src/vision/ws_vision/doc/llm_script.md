## 1. 개요

### 1.1 이 모듈이 존재하는 이유

`src/vision/README.md` 의 **A(이미지 → 지도)** 는 입력 계약이
*"흰 배경 고양이 라인아트/실루엣이 들어온다"* 이다. 그 라인아트를 **누가 만드는지**가
설계 전체에서 비어 있었다.

dy 의 SAM3 경로도 같은 빈틈을 가지고 있다. 실측(2026-08-16)으로 확인한 것은,
`sam3_extract_ros_node.py` 가 받는 입력이 **손으로 구해다 놓은 벡터풍 일러스트
`cat_char.png`** 라는 사실이다. 파이프라인은 캐리커쳐를 소비하도록 이미 만들어져 있고,
**그 캐리커쳐의 출처만 사람**이다.

이 모듈은 그 자리 하나를 메운다 — 사용자의 실물 고양이 사진에서 같은 형식의 그림을
자동으로 만들어낸다.

> **바꿔 말하면** 이 모듈의 사양은 "좋은 그림을 그린다"가 아니라
> **"`cat_char.png` 을 사진에서 재현한다"** 이다. 목표물이 리포 안에 실물로 있다는 것이
> 이 작업의 가장 좋은 조건이다 — 비교 대상이 말이 아니라 파일이다.

### 1.2 왜 직렬인가

검토 중에 병렬 구조를 후보로 놓았다. *실물 사진에 SAM3 를 돌려 부위를 따고, 따로 만든
캐리커쳐와 합친다* 는 안이었다. **폐기했다.**

폐기 근거는 좌표계다. 사진과 생성 이미지는 서로 다른 좌표계를 가지며, 고양이의 위치·
크기·자세가 조금만 달라져도 마스크가 그림 위에 얹히지 않는다. 그 정합을 풀려면 새로운
상자(③ 합치기)가 필요하고, 그 상자는 아무도 만들지 않았다.

직렬로 두면 **SAM3 가 캐리커쳐 위에서 돌아 좌표계가 하나뿐**이라 문제 자체가 생기지 않는다.
그리고 그것이 dy 코드의 현재 동작이다 — 설계를 현실에 맞춘 것이지 현실을 설계에 맞춘 것이
아니다.

### 1.3 설계 원칙

| 원칙 | 왜 |
|---|---|
| **경계는 파일 한 장** | ①의 출력은 PNG 파일이다. 토픽·타입을 dy 와 공유하지 않는다. 경계가 얇으면 이 모듈이 없어도 (손으로 구한 그림으로) 파이프라인이 계속 돈다 — 지금 dy 가 하고 있는 그대로다 |
| **동료 코드 무수정** | ②③은 한 줄도 고치지 않는다. 입력 경로 하드코딩조차 dy 몫으로 남긴다. 남의 작업을 인질로 잡지 않는다 |
| **전송 경로는 바이트만 다룬다** | `api_client` 와 `image_io` 는 `cv::Mat` 을 쓰지 않는다. API 가 낸 바이트와 저장한 바이트가 같아야, 프롬프트를 판정할 때 재인코딩 차이가 노이즈로 섞이지 않는다. 픽셀을 만지는 일은 **전처리·후처리라는 이름 붙은 단계에서만** 하고, 그 결과물은 원본과 나란히 따로 저장한다 (`image_ops`) |
| **프롬프트는 코드가 아니라 데이터** | 프롬프트는 반복 실험으로만 확정된다. 소스에 문자열로 박으면 한 글자 고칠 때마다 재빌드다. 파일로 두면 재빌드가 없고 git diff 에서 프롬프트 변화만 따로 읽힌다 |
| **호출 하나에 돈이 나간다** | 실수로 두 번 보내지 않는 것이 기능이다. 사전 견적 · 지문 기반 재사용 · 4xx 무재시도가 전부 이 원칙에서 나온다 |
| **판정은 사람이 한다** | 모듈은 "이게 라인아트인지" 판정하지 않는다. 판정하면 기준이 바뀔 때마다 모듈이 흔들리고, 같은 판정을 F1.2 적합성 검사와 두 곳에서 하게 된다 |
| **ROS 무의존 코어 + CLI 하네스** | `vision_core` 가 이미 선 방식이다. ROS 없이 단위 시험이 되고, 경계 형식을 나중에 정할 수 있다 |

### 1.4 성공을 무엇으로 보는가

**사람이 눈으로 판정한다.** 그래서 이 모듈의 하네스는 "돌았다"를 보고하는 도구가 아니라
**"같은 사진 × 프롬프트 3종을 나란히 놓고 보게 하는" 도구**다. 하네스의 목적이 곧 판정
방식에서 나온다.

참고 수치로 `cat_char.png` 의 SAM3 confidence(cat 0.9723 / eye 0.9077·0.9138 /
nose 0.8621 / mouth 0.8323)를 대조군으로 둔다. **게이트가 아니다** —
낮아도 그림이 좋으면 채택하고, 높아도 못 쓸 것이면 버린다.

## 2. 핵심기능

네 개다. **L1 이 본체이고 L2~L4 는 전부 "사람이 눈으로 판정한다"와 "호출에 돈이 나간다"는
두 조건에서 파생됐다.**

### L1. 사진 → 캐리커쳐

| | 내용 |
|---|---|
| 입력 | 실물 고양이 사진 1장 (PNG/JPEG/WebP, 50MB 미만) + 프롬프트 + 파라미터 |
| 출력 | 캐리커쳐 PNG 1장 (`cat_char.png` 형식) |
| 수단 | `POST /v1/images/edits`, `multipart/form-data`, `model=gpt-image-2`, 마스크 없음 |

**하는 일** — 바이트를 실어 보내고, base64 응답을 디코드해 바이트로 돌려준다.

**하지 않는 일**
- 결과가 캐리커쳐인지 판정하지 않는다 (원칙 §1.3)
- 픽셀을 손대지 않는다 — **`api_client` 안에서는** 후처리·이진화·리사이즈가 없다.
  그 일은 `image_ops` 가 이름 붙은 단계로 따로 한다
- 입력 사진의 적합성을 검사하지 않는다 (그것은 F1.2, vision 의 별개 함수)

**실패 처리의 갈림길이 하나 있다.** 4xx 는 요청이 틀린 것이므로 **재시도하지 않는다** —
재시도하면 같은 실패를 돈 내고 반복한다. 429·5xx 만 지수 백오프로 다시 보낸다.
이 구분을 호출부의 `if` 가 아니라 **예외를 만드는 자리**에 담아 한 번만 판정한다.

### L2. 프롬프트 관리

| | 내용 |
|---|---|
| 입력 | 프리셋 이름 (`conservative` · `balanced` · `minimal`) |
| 출력 | 프롬프트 문자열 |
| 형태 | 설치된 `prompts/<이름>.txt` — 소스가 아니라 데이터 |

3단계로 나눈 이유는 **어느 것이 쓸 만한지 실측으로만 정해지기 때문**이다. 하나를 골라
튜닝하는 것보다, 세 개를 같은 사진에 돌려 놓고 비교하는 편이 빠르게 수렴한다.

| 프리셋 | 의도 |
|---|---|
| `conservative` | 원본 고양이의 자세·비율·특징을 최대한 지킨다. 선이 많아질 수 있다 |
| `balanced` | 기본. `cat_char.png` 에 가장 가깝게 |
| `minimal` | 외곽 위주. 선이 가장 적어 N2(15분) 작화 예산에 유리하다 |

세 프롬프트 모두 **`cat_char.png` 의 특징을 요구문으로 옮긴다** — **정확히 3색**(검정 선 ·
중간 회색 채움 하나 · 밝은 배경 하나) · 두껍고 균일한 외곽선 · 그라데이션/해칭/스티플링
없음 · 눈 2개와 코와 입이 서로 닿지 않는 닫힌 도형 · 전신이 테두리에 닿지 않게.

> "3색" 인 이유와 "부위 나열"을 줄인 이유는 둘 다 실측에서 나왔다 —
> `llm_readme.md` §1 의 실측 두 절(목표물의 색 구조 · 최종 그림은 폐곡선 5개)을 볼 것.

> **예상 함정** (HANDOFF 08-03 이 지목했고 아직 유효하다) — 육안으로 선 그림이어도 실제로는
> 안티앨리어싱된 회색 그라데이션이라 이진화 임계값에 민감할 수 있다. 선을 면으로 그리면
> 이중 윤곽이 나온다. 해칭이 섞이면 스트로크 수가 폭발한다. **이 셋은 프롬프트로 막는다.**

### L3. 비용 방어

| | 내용 |
|---|---|
| 입력 | 파라미터 · 입력 사진 |
| 출력 | 예상 비용(USD) · 요청 지문 |

**호출 전 견적** — 크기·품질로 예상 비용을 계산해 보여주고, 명시적 동의 없이는 보내지
않는다. gpt-image-2 는 장당 정가가 없고 토큰 과금이라, 품질을 한 칸 올리면 비용이
자릿수로 뛴다 (low $0.006 → high $0.211, 약 35배).

**기본 품질을 `low` 로 둔다.** 프롬프트 확정 단계에서 회차가 가장 많이 돌기 때문이다.
확정된 뒤에 품질을 올린다.

**요청 지문** — 입력 사진·프롬프트·파라미터를 하나의 지문으로 접어 산출물 파일명에 넣는다.
같은 요청이면 이미 있는 결과를 재사용해 **같은 돈을 두 번 내지 않는다.** 부수 효과로
"이 PNG 가 어떤 프롬프트에서 나왔나"가 파일명만으로 되짚힌다.

**모델을 별칭으로 고정하지 않는다** — 프롬프트를 확정한 뒤에는 `gpt-image-2-2026-04-21`
같은 스냅샷으로 못박는다. 별칭은 OpenAI 가 스냅샷을 올릴 때 결과가 말없이 바뀐다.

### L4. 결과 확인 하네스

| | 내용 |
|---|---|
| 입력 | 사진 1장 |
| 출력 | 프리셋별 PNG + 무엇이 어떤 조건에서 나왔는지 적힌 요약 |

**판정이 사람 눈이므로 하네스의 목적은 "비교하기 쉽게 늘어놓는 것"이다.**
`vision_core` 의 `stroke_map_cli` 가 선 방식을 그대로 따른다 — 숫자는 stdout, 그림은
파일, 산출물은 호스트에 마운트된 `data/` 로 떨어져 컨테이너 밖에서 바로 열린다.

한 번 실행으로 프리셋 3종을 같은 사진에 돌리고, 각 결과에 어떤 프롬프트·크기·품질·비용이
붙었는지 함께 남긴다. **비교의 재료가 흩어지면 판정이 안 된다.**
