## 2. 🔴 불일치 — 실물 연동 전에 반드시 정한다

### 🔴1. 픽셀 → mm 축척 규칙 — **문서와 답변이 다르다**

| 출처 | 규칙 |
|---|---|
| **V-DOC** | `F2.4 ScaleToPaper` ✅ 구현됨 — **"letterbox 중앙정렬·여백·closed 판정"** |
| **V-ANS** | **bbox 긴변**이 목표 크기가 되도록. `s = 100 / 527`. **"이미지 크기는 계산에 쓰이고 있지 않다"** |
| **M-IMP** | `computePaperFit()` — **이미지 전체 크기** letterbox. `min(180/W, 267/H)` |

우리 구현은 V-DOC 을 따라 만든 것이라 V-ANS 와 어긋난다. 1280×960 이미지 예:

| | 계산 | scale |
|---|---|---|
| M-IMP (이미지 letterbox) | `min(180/1280, 267/960)` | **0.1406 mm/px** |
| V-ANS (bbox 긴변 → 100 mm) | `100/527` | **0.1898 mm/px** |

**같은 픽셀이 서로 다른 mm 가 된다.** 그림 크기와 위치가 조용히 틀어질 뿐 에러는 없다.

> ⚠️ **우리 문서의 "비전 원본 공식과 소수점까지 일치" 는 근거가 없다.**
> 그 검증은 **우리가 만든 가짜 발행자**로 한 것이라, 우리 가정을 우리가 확인한 셈이다
> ([`Pipeline Integration Status.md`](Pipeline%20Integration%20Status.md) §3 을 고쳐야 한다).

**V-DOC 은 letterbox 를 두 곳에서 말한다** — 오타가 아니다:

```
규약 절     : 배치 — 종횡비 유지 → 작화영역에 맞춰 축소 → 중앙 정렬(letterbox)
구현 상태 표 : F2.4 ScaleToPaper  ✅ 구현됨 — letterbox 중앙정렬·여백·closed 판정
```

**둘 다 참일 수 있는 시나리오가 있다.** V-DOC 에는 이런 문장이 있다:

> **경계 전달 형식(토픽/서비스/메시지 타입)은 아직 정하지 않았다** — 코어를 ROS 무관
> 라이브러리로 분리해 둔 이유가 이 결정을 moveit2 착수 시점까지 늦출 수 있어서다

즉 V-DOC 은 **`vision_core`(코어 라이브러리)** 를 설명한 문서이고 ROS 노드는 그 뒤에
생겼다. 그렇다면:

| 경로 | 만드는 곳 | 축척 |
|---|---|---|
| `map.csv` | `stroke_map_cli` → `vision_core::ScaleToPaper` | **letterbox** |
| `/vision/strokes` | `vision_node` | **bbox?** |

**둘이 실제로 다를 수 있다.** 그러면 우리 문서가 전제한 *"어느 쪽으로 들어와도 결국
mm 로 수렴하므로 시뮬레이션 검증 경로가 끊기지 않는다"* 가 **깨진다** — 파일로 검증한
결과와 토픽으로 그린 결과가 달라진다.

**정해야 할 것**

1. 현재 코드가 letterbox 인가 bbox 인가? (V-DOC 이 낡은 것인지 확인)
2. bbox 방식이면 **목표 긴변 크기**는 얼마이고 고정값인가 파라미터인가?
3. **`map.csv` 와 `/vision/strokes` 가 같은 규칙을 쓰는가?** — 위 시나리오 때문에
   이게 **가장 중요한 질문**이다. 다르면 검증 경로 자체가 무너진다.

> bbox 방식이어도 우리가 재현할 수 있다 — bbox 는 받은 스트로크 전체에서 계산 가능하다
> (V-ANS: "cat 만이 아니라 **모든 부위를 합친 bbox**"). **목표 크기 값 하나만** 주면 된다.

### 🔴2. 종이 mm → 로봇 XY 방향 — **우리 숙제**

V-DOC 의 좌표 규약:

```
종이 좌상단이 (0,0), +x 오른쪽, +y 아래쪽   (이미지 픽셀과 같은 방향)
```

V-ANS 가 인용한 `hcr5_examples/draw_contour.cpp` 의 로봇 매핑:

```
관찰자(베이스에서 +X 를 봄) 기준   위쪽(멀어지는 쪽) = +X,  왼쪽 = +Y

x = cx − (v − v_c)·s        ← 이미지 v(아래로 증가) 에 음부호
y = cy − (u − u_c)·s        ← 이미지 u(오른쪽으로 증가) 에 음부호
```

즉 **종이 y → 로봇 −X**, **종이 x → 로봇 −Y** (스왑 + 양쪽 음부호).

우리 `flangePose()` 는 그렇게 하지 않는다:

```cpp
p.x = px0 + (mx_mm - center_x_mm) * scale - tip_offset.x;   // 종이 x → 로봇 +X
p.y = py0 + (my_mm - center_y_mm) * scale - tip_offset.y;   // 종이 y → 로봇 +Y
```

**스왑도 부호반전도 없다. 결과적으로 90° 회전 + 거울상이 될 수 있다.**

> ⚠️ **지금까지 이게 안 드러난 이유:** ① 시뮬에서 아주 작게(수 cm) 그렸고 ② 검증을
> `trace_cli` 로 했는데 그건 **종이 좌표계**에서 비교하므로 로봇 쪽 방향 오류가 보이지
> 않는다 ③ `use_current_pose_as_origin: true` 라 원점이 로봇 현재 자세를 따라간다.

**이건 비전에 물을 것이 아니라 우리가 정할 것이다.** 다만 예제의 관찰자 규약이 실제
설치 방향과 같은지(종이를 로봇 앞 어느 방향으로 놓는지)는 확인이 필요하다.

### 🔴3. `closed` 가 ROS 메시지에 없다

| 출처 | |
|---|---|
| **V-DOC** | C++ `struct Stroke { std::vector<Point2> points; **bool closed{false};** }` |
| **메시지** | `Stroke.msg` — `instance_label`, `image_width`, `image_height`, `points` 뿐 |
| **M-IMP** | 토픽으로 받으면 **무조건 `closed = true`** 로 둔다 |

**비전 내부에는 있는 정보가 ROS 메시지를 건너면서 사라진다.** `map.csv` 에는 `closed`
열이 있어서 파일 경로에서는 살아 있다 — **토픽 경로만 정보가 준다.**

열린 스트로크(수염 같은 것)가 오면 우리가 억지로 닫아 버려 **없는 선을 하나 그린다.**
`use_thinning: true`(centerline)를 쓰면 열린 폴리라인이 나오는 것이 자연스럽다.

**정해야 할 것:** `Stroke.msg` 에 `bool closed` 를 넣을 수 있는가? (넣으면 타입 해시가
바뀌므로 양쪽 동시 재빌드가 필요하다.)

## 2.5 🔴4. AC2 — **정의에 따라 통과와 미달이 갈린다**

우리 인수 기준이다. `src/moveit2/README.md` 담당범위 표:

> F3.1 스트로크 순서 최적화 — **AC2: 무최적화 대비 이동시간 20 % 이상 단축**

`src/operator/README.md` 는 이걸 코드로 못박아 두었다:

```cpp
struct PlanSummary { int stroke_count; double draw_len_mm,
                     travel_before_s, travel_after_s; };   // F3.3 → AC2
double OptimizationGainRatio(const PlanSummary &);
bool   MeetsAc2(const PlanSummary &, double th = 0.20);
```

즉 판정식은 **`(travel_before_s − travel_after_s) / travel_before_s ≥ 0.20`** —
전체 실행 시간이 아니라 **펜업 이동 시간**이다.

### 우리 실측을 대입하면

| `travel_after_s` 를 무엇으로 보나 | 값 | 비율 | 판정 |
|---|---|---|---|
| **NN 순서만** (F3.1 문자 그대로) | 0.57 s | **1.7 %** | ❌ **미달** |
| 순서 + 폐곡선 회전 | 0.51 s | **12.1 %** | ❌ **미달** |
| 순서 + 회전 + **이동 가속 상향** | 0.16 s | **72.4 %** | ✅ 통과 |

(`travel_before_s` = 0.58 s, 최적화 전부 끈 상태. 출처:
[`Trajectory Optimization.md`](Trajectory%20Optimization.md))

### 그래서 무엇이 문제인가

AC2 는 **F3.1(순서 최적화)** 항목에 달려 있다. 그런데 **순서 최적화만으로는 1.7 %**
밖에 안 나온다 — 20 % 를 크게 밑돈다. 20 % 를 넘기는 것은 **가속 배율 상향**이고,
그건 순서 최적화가 아니라 다른 손잡이다.

> ⚠️ **이건 구현이 부족해서가 아니다.** 펜업 이동이 실제 4.5 ~ 24 mm 라 순항 구간 없이
> 가감속만 하고, 그래서 시간이 거리에 `√` 로만 붙는다. 거리를 41 % 줄여도 시간은 12 %
> 밖에 안 준다. **AC2 를 세울 때 이 물리를 몰랐던 것**이지 최적화가 안 된 게 아니다.

### 정해야 할 것 — 팀 전체

1. **`travel_after_s` 에 이동 가속 상향을 포함하는가?** "무최적화 대비" 의 *무최적화* 가
   ① F3.1 만 끈 상태인지 ② moveit2 의 이동 관련 최적화를 전부 끈 상태인지.
   ②로 보면 **72.4 % 로 여유 있게 통과**한다.
2. AC2 를 **F3.1 항목에서 떼어** "moveit2 이동 최적화" 로 옮길 것인가?
3. 아니면 임계값(20 %)을 조정할 것인가?

**어느 쪽이든 데이터는 다 있다.** 지금 정하지 않으면 나중에 결과 해석에서 다툰다.

## 2.6 🔴5·6. operator 가 우리에게 기대하는 것 — **전부 미구현**

`src/operator/README.md` 를 보면 operator 는 moveit2 로부터 다음을 받는다고 가정한다.
**우리 쪽에 대응 구현이 하나도 없다.**

| 기대하는 것 | 우리 현황 |
|---|---|
| `PlanSummary { stroke_count, draw_len_mm, travel_before_s, travel_after_s }` | ❌ 없음. 로그로만 출력 |
| `strokes_done`, `failed_strokes[]`, `aborted_at_stroke` | ❌ `drawn` 카운터만 있고 보고 안 함 |
| `Command { Start, EmergencyStop, Pause, Resume, ... }` 수신 | ❌ 없음. 노드가 뜨면 바로 그리고 끝난다 |
| `Event { PlanReady, StrokeDone, StrokeFailed, DrawingDone, ... }` 발행 | ❌ 없음 |

moveit2 README 의 **F4.3(실행·진행 보고)** · **F4.4(실패 처리)** 가 이것인데 아직
착수 전이다.

> ⚠️ **`travel_before_s` 는 지금 구조로는 못 낸다.** 우리는 최적화 전/후의 **거리**
> (`before_mm`·`after_mm`)를 재고 있는데 AC2 가 요구하는 것은 **초**다. 내려면
> **최적화 전 순서로도 궤적을 계획해서** 그 duration 을 재야 한다 (실행은 불필요,
> 계획만 하면 된다). 계획 비용은 웨이포인트 100 개 기준 12 ~ 50 ms 라 부담은 없다.

## 2.7 🟡18·19. 종이 → 로봇 변환의 진짜 주인은 캘리브레이션(F5)

🔴2 를 "우리 숙제" 라고 썼는데, 더 정확히는 **캘리브레이션이 답을 주기로 되어 있는
자리**다. 비전 README:

> - z 없음 — **z 는 moveit2 쪽(F4.1)이 캘리브레이션으로 붙인다**
> - calibration(F5)은 **moveit2 가 이 지도를 로봇 좌표로 옮기는 데만 쓰인다**

지금 우리는 그걸 `paper.use_current_pose_as_origin: true` 로 **대체**하고 있다 —
"현재 자세가 곧 종이 원점" 이라고 치는 것이다. 그래서:

- 종이가 로봇 앞 **어느 위치·방향**에 놓이는지 아무도 정하지 않았다
- 종이 평면의 **z(높이)** 도 마찬가지다
- 🔴2 의 스왑·부호 문제도 결국 이 변환 행렬 하나로 결정된다

비전 README 에 열린 질문도 하나 남아 있다:

> F5.2용 마커가 **지그에 고정**되어 있는지 확인 필요 (종이 쪽에 있으면 "F5.2는 1회"
> 라는 전제가 무너짐)

**정해야 할 것:** 캘리브레이션 착수 전까지 종이 위치를 어떻게 가정할 것인가. 지금처럼
"현재 자세 = 원점" 으로 계속 갈지, 임시로 고정 좌표를 정할지.

## 3. 🟡 미확인 · 미합의

### 🟡4. 메시지 타입 해시

필드 이름·타입·순서 중 하나라도 다르면 **토픽은 보이는데 메시지가 0 개** 들어오고
에러가 없다. 우리 미러 정의 기준값:

```
RIHS01_d8c0b1c8ffdbe600b7b59775cc2460b82c96be241faf49fea80c7393e77506d7
```

```bash
ros2 topic info /vision/strokes --verbose | grep -i "type hash"
```

> 🔴3 을 반영하면 이 값이 바뀐다. **한 번에 같이 처리하는 편이 낫다.**

### 🟡5. `resample_step_mm` — 우리 실행시간의 95 % 를 좌우한다

V-DOC 이 이미 정확히 짚어 두었다: *"**그대로 moveit2 데카르트 waypoint 밀도가 된다.**
작을수록 선은 매끄럽지만 점 수가 늘어 N2 를 압박한다 — 실측 후 조정"*. 기본값 **1.0 mm**.

**그 "실측" 이 나왔다.** 2026-08-14 측정
([`Trajectory Optimization.md`](Trajectory%20Optimization.md)):

| | |
|---|---|
| 전체 실행 시간 중 **그리기** | **95 %** (펜업 이동은 4.8 %) |
| 스트로크 192 점 기준 그리기 | 3.18 s |

우리가 펜업 이동에서 짜낼 수 있는 건 다 짜냈다(−8.5 %). **여기서 더 줄이려면 점 개수
아니면 그리기 속도뿐이고, 점 개수는 비전 파라미터다.**

**논의할 것:** `resample_step_mm` 을 1.0 → 2.0 으로 올리면 점이 절반이 된다. 선 품질이
얼마나 나빠지는지는 비전 쪽이 판단할 몫이라, **우리가 값을 정하자는 게 아니라 이 손잡이가
시간에 직결된다는 사실을 공유**하는 것이다.

### 🟡6. 목표 그림 크기

🔴1 이 bbox 방식으로 확정되면 **양쪽이 같은 값을 알아야 한다.** V-ANS 예시는 100 mm.
지금 어디에도 합의된 기록이 없다.

### 🟡20. N2 — 전체 900 초 예산

`MeetsN2(Record&, budget_s = 900.0)` — 작업 하나가 **15 분** 안에 끝나야 한다.
비전 README 는 `TotalDrawLengthMm` 이 "N2 예산 추정의 입력" 이라고 적어 두었다.

우리 실측은 아직 **아주 작은 그림** 기준이다: 40 × 45 mm, 192 점, **3.34 초**.
A4 작화영역(180 × 267 mm)을 채우면 선 길이가 수십 배가 되므로 그대로 외삽하면 안 된다.
**실제 크기로 한 번 재야** N2 여유를 말할 수 있다.

> `AwaitingReview`(사람이 검토하는 동안 로봇이 서 있는 시간)도 N2 예산을 먹는다고
> operator README 에 적혀 있다 — 로봇 시간만으로 예산을 다 쓰면 안 된다.

### 🟡21. `instance_label` 이 한 이미지 안에서 유일한가 — **아니면 프레임 판정이 깨진다**

우리는 메시지에 `Header` 가 없어서 **라벨 중복을 "새 이미지 시작" 신호로 쓴다**
(`draw_cat.cpp` 의 `StrokeCollector::onStroke`).

```
같은 라벨이 또 왔다  →  이전 이미지가 끝났다고 판정하고 프레임을 확정
```

**한 이미지 안에 같은 라벨이 두 번 나오면** (예: 수염을 둘 다 `"whisker of cat"` 으로
보내는 경우) 한 이미지가 **두 프레임으로 쪼개지고, 우리는 최신 것만 쓰므로 앞부분을
버린다.** 에러는 안 난다.

**확인할 것:** 라벨이 한 이미지 안에서 유일함이 보장되는가? 아니면 `"...__2"` 같은
접미사를 붙여 주실 수 있는가? (`Header` 가 들어오면 이 문제 자체가 사라진다.)

### 🟡22. 픽셀 좌표가 `int32`

비전 내부는 `cv::Point2d`·`Point2{double}` 인데 `PixelPoint.msg` 는 `int32 u, v` 다.
메시지를 건너면서 **소수부가 버려진다.**

축척 0.19 mm/px 기준 최대 약 **0.19 mm** 의 양자화 오차이고, 더 중요한 것은
**`resample_step_mm: 1.0` 으로 균일하게 재샘플링한 간격이 정수 반올림으로 흐트러진다**는
점이다. 선 품질에 영향이 있는지는 비전팀이 판단할 몫이다.

> 파일 경로(`map.csv`)는 mm 실수라 이 문제가 없다 — **토픽 경로만 해당**된다.

### 🟡14. `ROS_DOMAIN_ID`

네 모듈 compose 가 전부 `${ROS_DOMAIN_ID:-0}` 인데 `run_container.sh` 는 이것만 export
하지 않는다. 2026-08-14 에 실제로 도메인 0 으로 생성돼 엉뚱한 컨테이너에 붙었다.
자세한 것은 [`Pipeline Integration Status.md`](Pipeline%20Integration%20Status.md) §5.

## 5. 비전팀에 보낼 질문 — 그대로 복사해서 쓰면 된다

> **1. 축척 규칙이 letterbox 인가요, bbox 긴변 기준인가요?**
> `src/vision/README.md` 에는 `ScaleToPaper` 가 "letterbox 중앙정렬" 로 되어 있는데,
> 주신 답변은 "bbox 긴변이 목표 크기가 되도록, 이미지 크기는 미사용" 이라 서로 다릅니다.
> 어느 쪽이 현재 코드인지 알려주시면 저희 변환을 맞추겠습니다.
>
> **2. (bbox 방식이라면) 목표 긴변 크기는 얼마이고, 고정값인가요 파라미터인가요?**
> bbox 자체는 받은 스트로크로 저희가 계산할 수 있어서, 이 값 하나만 있으면 됩니다.
>
> **3. `map.csv`(파일) 와 `/vision/strokes`(토픽) 가 같은 축척 규칙을 쓰나요?**
> 다르면 두 경로의 결과가 달라집니다.
>
> **4. `Stroke.msg` 에 `bool closed` 를 넣을 수 있을까요?**
> 비전 내부 `struct Stroke` 에는 있는데 ROS 메시지에는 없어서, 토픽으로 받으면 저희가
> 전부 폐곡선으로 간주합니다. 열린 스트로크(수염 등)가 오면 **없는 선을 하나 그립니다.**
> 넣으면 타입 해시가 바뀌니 양쪽 동시 재빌드가 필요합니다 — 하신다면 `Header` 추가도
> 같이 하는 편이 낫습니다.
>
> **5. `resample_step_mm` 을 조정할 여지가 있을까요? (판단은 비전팀 몫)**
> 실측 결과 저희 전체 실행 시간의 **95 % 가 그리기**이고, 그 시간은 점 개수에 직결됩니다.
> 1.0 → 2.0 이면 점이 절반입니다. 선 품질과의 균형은 비전팀이 아셔야 할 것 같아
> **값을 제안하는 게 아니라 이 손잡이가 시간에 직결된다는 사실만 공유**드립니다.
>
> **6. `instance_label` 이 한 이미지 안에서 유일한가요?**
> 메시지에 `Header` 가 없어서 저희는 **라벨 중복을 "새 이미지 시작" 신호로** 쓰고
> 있습니다. 한 이미지 안에 같은 라벨이 두 번 나오면(수염 둘을 같은 이름으로 보내는 등)
> 한 이미지가 두 프레임으로 쪼개지고 앞부분을 버립니다 — 에러 없이 그렇게 됩니다.
>
> **7. 픽셀 좌표가 `int32` 인데 괜찮을까요?**
> 비전 내부는 `double`(`cv::Point2d`)인데 메시지에서 정수로 잘립니다.
> `resample_step_mm` 으로 균일하게 맞춘 간격이 반올림으로 흐트러지는데, 선 품질에
> 영향이 있는지는 비전팀이 아실 것 같습니다. (`map.csv` 는 mm 실수라 해당 없습니다.)
>
> **8. 실물 발행이 되면 타입 해시 한 번만 대조해 주세요.**
> `ros2 topic info /vision/strokes --verbose | grep -i "type hash"`
> 저희 기준값: `RIHS01_d8c0b1c8ffdbe600b7b59775cc2460b82c96be241faf49fea80c7393e77506d7`
> 다르면 **토픽은 보이는데 메시지가 0 개** 들어오고 에러가 나지 않습니다.

### 팀 전체에 (비전팀 아님)

> **9. AC2 의 "무최적화 대비 이동시간 20 %" 에서 *무최적화* 의 범위를 정해 주세요.**
> 순서 최적화(F3.1)만으로는 **1.7 %** 이고, 저희 이동 최적화를 전부 포함하면
> **72.4 %** 입니다. 정의에 따라 통과와 미달이 갈립니다 (§2.5 에 근거 전부 있음).
>
> **10. operator 가 기대하는 `PlanSummary` 를 언제 구현할지 정해 주세요.**
> `travel_before_s` / `travel_after_s` 는 지금 거리(mm)로만 재고 있어서, 초 단위로
> 내려면 최적화 전 순서로도 궤적을 계획해 봐야 합니다 (§2.6).
>
> **11. 캘리브레이션 착수 전까지 종이 위치를 어떻게 가정할까요?**
> 지금은 `use_current_pose_as_origin: true` — "로봇 현재 자세가 곧 종이 원점" 으로
> 대체하고 있습니다. 종이가 로봇 앞 어느 위치·방향·높이에 놓이는지 정해진 것이
> 없습니다 (§2.7).
